# /ux-review — 화면 점검 → 오너 제안

## 역할
「우리 웹 살펴보고 빈약한 곳 + 바꾸는 방법」을 매번 같은 절차로 낸다(오너 「지금처럼 검토하고 나에게 제안하는 과정
자동화」 2026-10-16). 이 파일은 **점검 절차만** 담는다. 제안의 형식(규모 선언 · 선례 표 · 3문 · 목업 · 자기 검토)은
`/design-bank`가 정본이고, 원칙은 CLAUDE.md가 정본이다 — 여기 다시 쓰지 않는다.

**구현하지 않는다.** 산출물은 제안까지다. 구현은 오너가 고른 항목만, 그다음 세션에서 한다.

## 요청
$ARGUMENTS
(비어 있으면 웹(데스크톱) 전체 기본 점검. 「모바일」이 들어 있으면 `--mobile`을 붙인다 — 오너 2026-10-16
「일단 모바일은 제외하고 웹 위주로」가 풀리기 전까지 기본은 웹만)

## 0. 기계 측정 (건너뛰기 금지)

```bash
node scripts/ux-audit.mjs --start            # 웹만. 모바일 포함은 --mobile
npm run e2e:build && node scripts/ux-audit-auth.mjs --start   # 로그인 화면(복습 진행 · 끝, 서재 목록, 뷰어) — 합성 로그인
```

- 산출: `.ux-audit/<KST 날짜>/report.md` · `report.json` · 화면별 PNG(커밋하지 않는다).
- 로그인 점검 산출: `.ux-audit/<KST 날짜>/auth/report.md` — 화면마다 확인한 동작의 PASS/FAIL(앞면 클릭 펼치기 · 카드 넘김 효과 등).
  e2e 합성 백엔드(`e2e/fixtures/*`)를 그대로 쓰므로 운영 계정 · DB에 닿지 않는다. 빌드가 e2e 공개 값이 아니면 시작을 거부한다.
- Node 24에서 돈다(CLAUDE.md 개발 환경). 서버가 이미 떠 있으면 `--start` 없이.
- **PNG를 전부 직접 본다**(Read). 표의 숫자만 보고 판단하지 않는다.
- 플래그는 후보일 뿐이다. 예: 비로그인 「서재」의 빈 아래 63%는 로그인 유도 화면이라 의도일 수 있다 — 판단은 1단계에서.

## 1. 판단 — 플래그 + 화면 + 코드 대조

- 플래그마다: 진짜 문제인가 / 의도된 설계인가(관련 문서 · 계약 테스트 · 보드 확인) / 이미 열린 작업인가(`docs/ai-tasks.md`).
- **로그인 화면 중 `ux-audit-auth` 보고서에 없는 것(report.md 「미검증」 목록)은 코드로만 본다.** auth 보고서 화면은 합성 자료(단어 3개 ·
  자료 5개)라 양 · 모양이 실계정과 다를 수 있음을 붙인다. 결론에 반드시 「코드 대조 · 화면 미검증」을 붙인다.
  > 왜: 2026-10-16 점검에서 복습 끝 화면을 「토스트 한 줄」이라 했으나 `ReviewFinished` 요약 화면이 이미 있었다.
  > 코드로 본 것을 화면으로 본 것처럼 쓰면 같은 오판이 반복된다.
- 「없다」는 grep으로 찾아본 뒤에만 쓴다(`/design-bank` 1단계와 같다).
- 이미 고친 것 · 진행 중인 PR은 제외하고 링크만 단다.

## 2. 제안 — `/design-bank` 형식으로

- 항목마다 **증상 · 근거(파일:줄 또는 캡처) · 바꾸는 방법 · 규모(탐침/국소/구조)**. 우선순위는 사용자에게 보이는 영향 순.
- 화면이 바뀌는 항목은 **텍스트 목업**을 붙인다(CLAUDE.md UI 규약). 손으로 만져 봐야 판단되는 동작(넘김 · 전환 등)은
  실험 페이지(아티팩트)로 낸다 — 선례: [복습 손맛 실험실](https://claude.ai/artifact/XsicDi53PnFEmBXPgB3LnH).
- 선례 · 오픈소스 표(채택/부분 채택/배제 + 근거)는 새 의존성 · 새 패턴을 제안할 때만. 근거 없는 「업계 표준」 금지.
- 끝에 **오너가 고를 것 하나**를 묻는다(객관식, 권고안 먼저).

## 3. 전달

- 대화 세션이면: 대화에 바로 보고(KST 표기).
- 정기 실행(예약 작업)이면: 결과를 이슈 #1077(제안 백로그)에 코멘트 하나로 게시한다. 코멘트 첫 줄 =
  `🔎 UX 점검 <KST 날짜> — 제안 N건 · 오너 선택 대기`. 같은 항목이 직전 점검에도 있었으면 새로 쓰지 않고 「지난 점검 #N 그대로」로 묶는다.
- 커밋 · PR · 보드 변경은 하지 않는다(제안 단계). 시크릿 · 운영 DB · 환경 변수는 건드리지 않는다.

## 4. 자기 검토 (1회)

- 화면으로 확인한 것 / 코드로만 본 것 / 추정이 섞이지 않았는지 — 항목마다 셋 중 하나로 표시했는지.
- 지난 점검(#1077의 직전 🔎 코멘트)과 비교해 해결된 것 · 새로 생긴 것을 한 줄로.
