## 1. 결론

정본 사전(레퍼런스 어휘)의 단어마다 학습자 상태를 3단계로 **읽을 수 있게** 한다.

| 상태 | 뜻 | 데이터 |
|---|---|---|
| **만남** | 월드(NPC 대화·간판)·자료에서 이 말을 봤다 | **신설 — 이 RFC의 유일한 새 기록** |
| **담김** | 내 단어장(`user_vocabulary`)에 저장했다 | 기존 행 존재 여부의 파생 |
| **익힘** | FSRS 복습을 통과하고 있다 | 기존 `repetitions` 파생(상수 1곳) |

뒤 2개는 이미 있는 데이터의 파생이므로 신설이 없다. 새로 만드는 것은 "만났다"는 기록
하나이고, 그 기록으로 두 가지를 표시한다: **도시 카드의 "만난 말 n · 이 도시의 말 m"**
한 줄과, **뷰어·사전 목록의 상태 점**. 기록 지점은 런타임 형태소 분석이 아니라
**저작 시점에 콘텐츠에 박는 `refs` 주석**이다(결정적·전 트랙 동일 규약·검증 가능).

## 4. 설계

### 4.1 `refs` 주석 — 저작 시점 어휘 링크

npcScripts의 `say`·`ask` 스텝에 선택 필드 `refs: string[]`(정본 표기 배열)를 추가한다.
예: 라멘 스크립트의 첫 대사에 `refs: ['食券']`. 저작은 Claude 콘텐츠 영역(대사와 함께 작성).

- **계약 1(실재)**: 전수 테스트로 모든 refs가 일본어 정본 레지스트리에 존재해야 한다
  — 문법 챕터 slug 목록 대조(환각 차단)와 같은 패턴.
- **계약 2(배운 표현 그대로)**: `ask` 정답 선택지에 등장하는 ref는 같은 스크립트의 선행
  스텝 refs 또는 기반 챕터(ot-10-ramen 등) 어휘에 존재해야 한다. A-1 관례의 계약화 —
  런타임에 선택지를 숨기는 게 아니라 **저작을 묶는 vitest 계약**이다.
- 런타임 형태소 분석은 하지 않는다. fr(공백 분리)라 쉬워 보여도 동일하게 저작 주석 —
  전 트랙 동일 규약이어야 검증이 단순하다. (Lute의 파서 추상화·ZWS 오버레이는 임의
  텍스트용 해법 — 우리 텍스트는 전량 저작이므로 주석이 정답.)

### 4.2 만남 기록 — 게스트·로컬 우선

`NpcDialog`가 스텝을 소비할 때 해당 스텝 refs를 기록한다. 저장은 localStorage
`vocab-encounters:<lang>` (예: `vocab-encounters:ja`).

- storage-schema.md v1 규약 준수: 키는 storageSchema.js에만 정의, 정렬된 중복 없는
  `string[]` JSON, 소비 시 정본 레지스트리와 교집합(유령 표기 제외), 깨진 JSON·비배열은
  빈 배열, 저장 차단은 조용한 no-op. v1에 키 추가만이라 스키마 마이그레이션 불필요.
- `npc-met:<cityId>`가 같은 계열의 확립 선례다(만남의 대상이 사람→말로 바뀔 뿐).

### 4.3 상태 판독 — 전부 파생

```
vocabEncounterState(word):
  익힘  ← user_vocabulary.repetitions ≥ 2      (상수 ENCOUNTER_LEARNED_REPS 1곳)
  담김  ← user_vocabulary 행 존재               (fetchSavedWordSet 재사용)
  만남  ← vocab-encounters:<lang> 포함
  (우선순위 익힘 > 담김 > 만남, 해당 없음은 무표기)
```

새 테이블·새 SRS 필드·기존 경로 변경 없음. Anki 격차(상태 머신 등)는 audit-card-srs의
별도 트랙이며 이 RFC는 그 결론과 독립이다(어느 쪽이 채택돼도 '담김·익힘'은 파생으로 성립).

### 4.4 도시 이해도 — "이 도시의 말"

도시 코퍼스 = 그 도시 NPC 스크립트 refs의 합집합(모듈 시점 파생 상수 — 결정적, 테스트로
개수 고정. 간판 refs는 R3에서 합류). 표시는 **분수**("만난 말 5 · 이 도시의 말 12") —
초기 콘텐츠는 분모가 작아 %가 과장된다. 보상·칭호·마일스톤과 연결하지 않는다(비목표).

### 4.5 서버 정본 — 구현 (2026-08-22 오너 gate 해제 "ㄱㄱ")

`user_vocab_encounters (user_id, lang, word_text, first_met_at)` — PK(user_id, lang,
word_text), own-only RLS(select/insert만 — 만남은 불변이라 update/delete 정책 없음).
마이그레이션은 `supabase/migrations/20260822160000_user_vocab_encounters.sql`, 적용은
main 병합 시 CI(supabase-migrations.yml)의 `supabase db push` 관례를 따른다.

동기화는 `vocabEncounterSync.syncVocabEncounters` — **로컬이 원본**이라는 §4.2 철학
그대로, 로그인 시 학습 웹 진입점 2곳(레퍼런스 어휘 metSet·뷰어 metWordSet effect)에서
쌍방 병합만 한다: pull(서버 행을 로컬 합집합) + push(로컬 전용분 insert,
ignoreDuplicates로 서버 first_met_at 보존). 언어별 5분 스로틀(sessionStorage,
refProgress 선례), 실패·게스트·마이그레이션 미적용은 전부 조용히 로컬 단독(무해성 계약
— vocabEncounterSync.test.js가 고정). 기록 지점(NpcDialog·GameCanvas·뷰어 드래그)은
무변경 — 쓰기 시 서버 왕복을 더하지 않는다.

### 4.6 노드 텍스트 refs (R3 잔여 — 2026-08-22 저작 설계, 오너 "진행해")

실측 결과 '간판'(cityDistrictBoundarySigns)은 언어 콘텐츠가 아니라 지구 잠금 경계
표지물이었다. 실제 노출면은 **도시 노드의 name·desc를 A로 여는 GBC 설명 박스**다
(spot·shop 중 gate·chapter·npc·reading이 아닌 노드 — GameCanvas descOpen 경로).

- **필드**: 노드에 `refs: string[]`(정본 표기) + `refsLang: 'ja'`. refs가 있으면
  refsLang 필수(스크립트 lang 계약과 동일, R1 규칙대로 ja만).
- **저작 원칙 — 표기 실등장**: 그 표기가 노드 name·desc에 실제 문자열로 등장하는
  정본 어휘만 refs로 삼는다(요미·한글 번역만 있는 경우 제외). 이 원칙은 계약
  테스트가 기계적으로 강제한다(ref ⊆ name+desc).
- **기록 시점**: 설명 박스 열람(descOpen) 순간 — NpcDialog 스텝 노출 기록과 같은
  "본 순간" 원칙.
- **코퍼스**: cityVocabCorpus가 노드 refs도 합산 — 도시 카드 분모가 자란다.
- **1차 저작 범위**: 후쿠오카(港·タワー·神社·ラーメン·城·公園)·교토(城·神社·寺·市場).
- **도어 노드 편입(2026-08-22 확장, 오너 "이어서 ㄱㄱ")**: chapter 도어 프롬프트에
  desc를 병기(게이트 프롬프트의 desc 병기와 같은 문법)하고, 프롬프트가 열리는 순간
  refs를 기록한다. 오버월드 비게이트 노드는 기존 설명 박스 경로로 이미 기록되므로
  저작만 추가(1차 12노드 — 계약은 worldNodeRefs.test 전수).
- **제외(유지)**: 게이트 노드(전수 스캔 결과 desc에 정본 표기 실등장이 0 — 저작
  대상 자체가 없음), NPC 노드의 노드 desc(전국맵 라멘·신사 — 말걸기 프롬프트가
  name만 표시해 desc 미노출, 스크립트 refs가 소관).

### 4.7 fr/zh 뷰어 만남 (2026-08-22 오너 "fr/zh 뷰어 만남 확장 ㄱㄱ" — 학습 웹 2차 배치)

뷰어 드래그 기록의 ja 하드코딩을 언어별 정본 조회로 일반화한다(refVocabLookup — ja는
기존 findWord 위임 불변, fr/zh는 refLangs 레지스트리에서 표제어 키 인덱스를 지연 구축,
학습 순서 첫 등록 우선 = ja N5 우선과 동일 원칙).

- **대조 키**: fr는 표제어 정규화(관사·엘리지옹·괄호·대안 접기 — 본편·FLELex 병합
  dedup의 `_normFr`를 refWordNormalize로 이관해 병합·대조가 **단일 원천**), zh는 표기가
  곧 표제어(전수 실측 6,986어 — 괄호·대안·공백 0 → trim만), en은 소문자화만(전수 실측
  1,382어 — 대소문자 32건 Monday·TV류가 전부이고 토큰 base_form이 소문자 lemma. 관사
  시작은 관용구 8건뿐이라 fr와 달리 접지 않는다), ja는 원문 그대로(불변).
- **기록 표기 = 저작형 refMain 그대로**("la famille") — 레퍼런스 어휘 [만난 말] 필터의
  exact refMain 비교·서버 정본(§4.5) word_text와 같은 문자열. 뷰어 만남 점만 정규화 키로
  비교한다(저작형 "la famille" ↔ 토큰 "famille"; ja·en은 키가 항등이라 동작 불변).
- **전제 수리**: 프랑스어 자료는 전용 토크나이저 없이 tokenizeEnLine을 공용하는데,
  ASCII 한정 패턴이 café→caf로 단어를 끊어 대조 자체가 불가했다 — 라틴-1(악상·Œœ)
  확장으로 수리(영어 ASCII 동작 불변, 기존 핀 유지).
- **선례 조사**(규약): 채택 = 내부 `_normFr`(같은 코퍼스의 병합 dedup으로 이미 검증).
  부분 채택 = En 토크나이저 재사용(악상만 수리 — 전용 fr 토크나이저 신설은 배제, 만남
  대조에 과분). 배제 = 프랑스어 렘마타이저(Lefff·spaCy류 — 서버 의존·용량 대비 만남은
  하한 기록이라 표면형 매칭의 미달이 무해; 굴절 대응이 필요해지면 별도 gate).
- **한계(비목표 명기)**: fr 굴절형(vais→aller) 미대응, 다단어 표제어("bonne nuit"·
  "good morning")는 단일 토큰과 미대조 — 표면형≈표제어인 경우만 잡는 보수적 하한.
  en은 토크나이저 lemma(ran→run)가 굴절을 접으므로 fr보다 회수율이 높다.
- **en 편입(2026-08-22 오너 "en 뷰어 기록도 ㄱㄱ")**: 초판의 en 보류를 해제 —
  encounterLookupLang에 English를 더하고 en 로더(refLangs 레지스트리, w.en 키)를
  추가하면 나머지 경로(기록·점·필터·서버 동기화)는 이미 언어 중립이라 그대로 열린다.

## 5. 목업 (승인 대상 — 배치·정보량 합의용, 문구·기호는 교체 가능)

**A. NPC 대화 완주 화면** — 마지막 스텝 뒤, 스탬프 수집 줄 아래에 요약 한 블록:

```
  ── 🈁 오늘 만난 말 ──────────────────
  食券 しょっけん — 식권                [+ 담기]
  バリカタ — 면 아주 단단하게(하카타)    [+ 담기]
  お願いします — 부탁합니다              담김 ✓
  ─────────────────────────────────
              [ 닫기 ]
```

[+ 담기]는 기존 단어 저장 경로(`user_vocabulary`) 재사용. 이미 담긴 말은 버튼 대신 `담김 ✓`.
연출·포인트 없음 — 목록과 담기 버튼이 전부.

**B. 앨범 도시 카드** — 기존 카드에 한 줄 추가:

```
  🏯 후쿠오카          스탬프 3/5
     만난 말 5 · 이 도시의 말 12
```

만난 말 0인 도시는 줄 자체를 생략(빈 지표로 압박하지 않는다 — 분모만 있는 "0/12" 무표기).

**C. 뷰어 단어 목록** — 기존 급수 뱃지 옆 상태 점(무상태는 무표기):

```
  食券        [N3] ·   식권          (· 만남 — 월드에서 봄)
  券売機      [N2] ✓   자동판매기     (✓ 담김)
  お願いします [N5] ★   부탁합니다     (★ 익힘 — 복습 2회+)
```

**D. 레퍼런스 어휘(우리 사전) 목록** — 상단 필터 칩(수치는 예시):

```
  [전체 1,240] [만난 말 37] [담은 말 112] [익힌 말 41]
```
