## 1. 다음 차수의 목적

이미 구현한 기능을 하나의 출시 후보로 묶고, 교사 수업 → 학생 복습과 개인 필기 → 단어 정리 → 원문 복귀가 실제로 이어지는지 검증한다. 기능별 자동 검수는 상당 부분 완료됐으므로, 기존 검사를 단순히 더 많이 반복하기보다 서로 다른 기능·역할 사이의 연결을 확인한다.

사용자는 외출 중이다. 현재 세션에서 로그인하지 않아도 가능한 구현·합성 검수·미리보기 준비를 먼저 마치고 실제 계정과 물리 기기 검수는 분리한다.

구현 승인은 D1~D4의 코드·자동 검수·미리보기 준비 범위로 해석한다. 실제 운영 병합/승격은 해당 범위의 기존 유효한 승인을 확인한 뒤 수행한다. 이 설계 요청 자체를 병합 승인으로 쓰지 않는다.

## 4. 통합 방식

- 5개 PR을 각각 main에 squash하고 다시 쌓는 대신, #1320까지 포함된 새 `codex/*` 출시 브랜치를 만들고 main 대상으로 누적 변경을 한 번 검토하도록 제안한다. 예시 이름 `codex/classroom-release-20260917`은 착수 때 점유 여부를 확인한다.
- 조회 시점에는 main이 선조이므로 불필요한 충돌 해결이나 재작성은 필요 없다. 그 사이 main이 바뀌면 최신 main을 통합 브랜치에 병합하고 겹친 부분만 검토한다. force-push나 다른 세션의 변경 덮어쓰기를 하지 않는다.
- #1316~#1320의 구현 커밋과 검수 근거는 유지한다. 실제 통합 병합을 확인하기 전 기존 PR을 닫지 않는다. 통합 후에는 어떤 PR이 대체됐는지 링크로 정리한다.
- CI·Preview가 검수한 실행 커밋과 일치하는지 `/api/version`으로 확인한다. 고정 미리보기 주소를 쓰려면 현재 대상과 사용 중인 다른 작업을 먼저 확인한다. 이번 준비에서 임의로 공유 alias를 바꾸지 않는다.
- 새 DB·환경 변수는 기본 범위에 없다. 기존 저장 API·권한·마이그레이션 호환성을 점검하고 누락이 있으면 근거를 별도 기록한다.
- 복귀는 코드 배포 단위로 설계한다. 설명판 DB나 사용자가 새로 저장한 필기를 되돌리거나 삭제하지 않는다. 구버전으로 웹만 되돌려도 새 저장 형식을 안전하게 처리하는지 사전 확인하며, 불가능하면 해당 버전을 복귀 대상으로 삼지 않는다.

## 5. 세 동선과 데이터 경계

### 교사: 설명 → 명시적으로 학생에게 남기기

```text
팀 홈 → 오늘 수업 → 교재/설명판
                  → 교재 표현 또는 직접 입력/필기 인식
                  → 여러 표현과 필기를 함께 배치
                  → 필요한 표현만 수업에 남기기
                  → 날짜별 학생 수업 기록 확인
```

설명판 계정 저장은 교사의 비공개 판 저장이다. 판에 놓기와 학생에게 공개하는 수업에 남기기는 계속 구분한다. 같은 표현을 다시 눌렀을 때 중복되지 않는지, 서로 다른 뜻은 섞이지 않는지, 실패 때 이미 성공한 항목을 다시 생성하지 않는지 확인한다. 기존 기능이 정확히 동작하면 버튼이나 확인창을 추가하지 않는다.

### 학생: 공개된 수업 → 개인 학습

```text
팀 홈 → 해당 날짜 → 수업 교재 / 선생님이 남긴 표현
                 → 허용된 개인 자료 뷰어
                 → 단어 뜻·독음 확인 → 내 단어장 담기 → 원문 복귀
```

교사의 비공개 판·개인 초안·정리 전 후보는 학생에게 노출하지 않는다. 학생 화면의 편집 버튼 부재뿐 아니라 직접 API 요청도 검사한다. 기존 팀 참여·교재 접근/개인 사본 정책을 그대로 사용한다. 팀 자료를 개인 자료처럼 무조건 열 수 있게 권한을 넓히지 않는다. 교사 판 수정과 학생 개인 사본·단어장 수정이 서로 무엇을 바꾸는지 기존 계약과 대조한다.

### 개인 학습: 지금 필기 → 나중에 단어 정리

```text
내 서재 → 개인 노트 → 필기 → 선택 영역 인식 → 계속 필기
                     → 나중에 미완료 후보 확인
                     → 표기·독음·뜻 선택 → 선택한 항목 담기
                     → 다음 방문에 미완료부터 이어 정리
```

인식만으로 단어장 저장이나 복습 채점을 실행하지 않는다. 히라가나에서 다른 한자 후보를 골랐을 때 독음/뜻/확인 상태가 함께 일관되게 바뀌는지 확인한다. 직접 입력한 뜻을 후보 기본 뜻으로 덮어쓰지 않으며, 다른 의미의 기존 단어와 합쳐지지 않아야 한다. 부분 성공 후 실패만 다시 시도하고 기존 복습 일정은 유지한다.

이 동선은 기존 `NoteRecognition`, `NoteVocabulary`, `StudyNotePage`, `BoardInkRecognition`, 공통 저장 API를 재사용한다. 세 화면을 하나의 거대한 공통 편집기로 합치지 않는다.

## 6. 화면 설계 범위

새 홈·탭·대시보드를 추가하지 않는다. 설명판은 지금처럼 캔버스와 아이콘 메뉴를 중심으로 두고, 오류나 안내는 행동이 일어난 기존 패널에서 표시한다.

아래는 일본어 대응 영역에서 현재 뜻/품사와 출처를 구분하는 텍스트 설계다. 예시 데이터는 구현 데이터가 아니다.

```text
표제어                         현재 선택한 한국어 뜻
                               품사

일본식 자형     …
같은 뜻        …               기존 사전 / AI
```

- 단어 위 독음·아래 훈음·오른쪽 뜻, 여러 단어/필기 병치, 테두리 ON/OFF는 유지한다.
- 기존 사전/AI 표시를 재사용하고 별도 인증 배지나 근거 없는 정확도 %를 만들지 않는다.
- AI 대응을 찾는 요청과 캐시를 사용자·표기·선택 뜻·품사·자형 기준으로 나눈다. 품사가 없으면 없음을 유지하고 추측해서 채우지 않는다.
- 단어나 선택 뜻/품사가 바뀌면 이전 수동 조회 상태를 함께 초기화한다. 한 번 클릭했다고 바뀐 조건에 대해 자동 AI 재요청하지 않는다.
- 늦게 도착한 응답은 당시 선택 범위에서만 반영하고, 사용자의 직접 수정과 다른 선택을 덮어쓰지 않는다.
- 현재 단어·뜻·품사만 기존 공급자로 보낸다. 이번 작업에서 전체 수업/개인 노트를 추가 전송하지 않는다.
- 결과가 없으면 재시도와 기존 직접 입력을 제공한다. 교사의 설명·필기·저장 흐름은 계속 사용할 수 있어야 한다.

## 7. 뜻 정확성의 검수 설계

초기 24사례를 근거 확인용으로 만든다: 중국어 12, 일본어 8, 영어/프랑스어 각 2. 다의자·다의어·품사 차이·동형이의·히라가나→한자 후보·직접 수정·누락을 고르게 포함한다. 기존 60개 표시 사례와 목적을 구분한다.

각 사례에 원어, 선택한 뜻, 품사, 독음, 허용/금지 대응, 출처 URL, 확인일, 판단 근거를 붙인다. 한 가지 번역만 정답으로 못 박기보다 현재 의미와 맞는 표현의 허용 범위를 정의한다. 불확실한 사례는 보류로 표시하고 AI 출력 자체를 정답으로 삼지 않는다. 사전 본문을 대량 복제하지 않고 필요한 사실과 자체 설명만 남긴다.

두 검수 층을 구분한다. ① 고정 응답으로 뜻/품사 분기·캐시·늦은 응답·직접 수정 보존을 자동 검사 ② 근거를 확인한 어휘와 필요할 때 명시적으로 실행한 실제 공급자 응답을 비교한다. ① 통과를 실제 AI 전체 정확도 보장으로 보고하지 않는다. 기존 사용자 단어장·교재·판의 뜻은 일괄 재분석/수정하지 않는다.

## 8. 검수 묶음

| 묶음 | 원격 자동 검수 | 실제 계정/기기 검수 |
|---|---|---|
| 교사→학생 | 서로 다른 사용자 문맥에서 공개 표현·비공개 판·직접 API 권한·중복/실패 확인 | 다른 계정으로 수업 입장→교재 열기→표현 확인 |
| 개인 노트 | 2회 이상 인식/재접속·미완료/담음/제외·부분 저장·원문 복귀 | 기존 노트에서 누적 후보·단어장 기록 확인 |
| 저장·복구 | 연결 끊김·응답 유실·동시 수정·느린 읽기 중 필기 보존 | 실제 계정 저장→새 접속에서 복원 |
| 태블릿 | 390/768/1024px·키보드 초점·가로 넘침·회전 크기 변화 | Pencil/손바닥·실제 소프트 키보드·회전 |
| 언어 | 뜻/품사별 캐시·선택 전환·독음/훈음·직접 수정 보존 | 애매한 어휘의 의미 확인 및 실제 공급자 표본 |

기존 E2E의 개별 기능 검사는 그대로 쓰고 부족한 연결 시나리오만 추가한다. 사용자 역할은 Playwright의 별도 browser context로 나누며 권한 판정까지 무조건 성공하는 mock을 만들지 않는다. 기존 로컬 DB/권한 fixture를 재사용한다. 자동 검수를 실제 운영 로그인/DB 검수로 표시하지 않는다.

## 10. 납품 및 완료 판단

- main 대상 통합 draft PR 하나, 실제 실행 버전이 일치하는 Preview 하나.
- 3개 동선의 검수 결과와 대표 화면, 재현 가능한 실패/복구 기록.

- 기존 원본·판·개인 단어·복습 일정 보존 확인, 버전 복귀 계획.
- 실제 계정/기기에서 확인할 항목을 짧은 순서로 정리.

로그인 없이 여기까지 준비한다. 실제 운영 출시 완료는 실계정 검수와 승인된 병합/배포 확인까지 구분한다. 저장소 자동 수거/삭제, 새 시험 기능, PDF 조판, 신규 음성, 새 AI 공급자, 전면 디자인 재변경은 다음 범위로 남긴다. 특히 미참조 객체 정리는 최신/직전/충돌/진행 중 업로드를 구별해야 하므로 통합 준비에 끼워 삭제하지 않는다.
