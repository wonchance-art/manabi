## 가장 적은 변경으로 내보내는 경로

다음 한 과제는 **고정한 N5 개정판의 출시 경로 확정과 남은 출시 장애 확인**이다.

‘N5 전체를 깔끔하게 분리’하거나 새로운 CMS·권한 체계·베타 회원 시스템·대시보드를 만드는 것을 목표로 삼지 않는다.
분리 자체가 큰 재설계가 되면 필요한 변경과 비용/위험을 기록하고 경로를 재평가한다. 자동으로 재설계 범위를 늘리지 않는다.

교재를 먼저 출시한다는 합의가 통합 전체의 미충족 조건을 지우지 않는다. 교재 전용 경로를 택하면 실제 배포 변경과 공통 코드 영향까지 확인한다.
별도 후보를 추출하거나 제품을 수정하면 그 후보의 필요한 검사를 수행하며, 기존 통합 CI 성공을 무조건 이식하지 않는다.
최종 경로의 기록은 포함 파일/의존성, 제외된 기능에 대한 영향, 필요한 검수, 배포·발행·복원 순서와 남은 승인/접근 조건까지여야 한다.

## 출시 조건과 발행 전후 검수

출시 조건을 다음으로 고정한다. 일반 개선 아이디어를 뒤늦게 필수 조건에 계속 추가하지 않는다.

1. 공개할 범위의 **알려진 오답·명백한 의미 오류**가 남아 있지 않다.
2. 읽기 → 문제 풀이 → 답안 보존/재접속 → 설명·원문 복귀의 핵심 동선이 막히지 않는다.
3. 기존 판본·답안·표현 출처·개인 뜻·FSRS 일정·자료 권한을 손상시키지 않는다.
4. 최종 출시 후보의 필수 검사와 실제 실행 버전·배포 확인이 통과한다.
5. 이전 공개판으로 복원할 수 있고, 발행 직후 핵심 학습 연결 재검수를 마친다.

| 시점 | 확인 내용과 증거 |
|---|---|
| 발행 전 | 알려진 원고 오류, 실제 계정의 후보 읽기·풀이·재접속·모바일/키보드, 기존 저장·권한·판본 계약, 배포된 파일/버전, 초안 충돌·공개 포인터·복원 준비. 미실행을 성공으로 기록하지 않는다. |
| 발행 직후 | 새 공개판에서 실제 표현 저장 → 복습 목록 → 정확한 판본/원문 복귀, 기존 기록·공개 접근의 보존. 문제 시 기본 공개판 복원과 후속 조치. |
| 사용하면서 | 설명이 어려워 멈춘 곳, 오답의 원인이 학습 부족인지 문항 모호성인지, 다음 날 이어 공부하기, 저장한 표현 찾기/원문 복귀. 실제 관찰로 후속 우선순위를 정한다. |

현재 미발행 후보는 개인 표현 저장을 제한한다. 따라서 그 상태에서 실제 새 판본의 표현 저장까지 완주하도록 요구하지 않는다.
발행 전에는 기존 실제 발행판 동작과 로컬 판본/저장 계약을 구분해 검증하고, 새 판본의 실제 저장은 발행 직후 확인한다.
검수를 위해 공유 DB의 공개 포인터를 임시로 바꾸지 않는다. **운영에 새 파일 배포·확인 → 발행 → 운영 사후 검수** 순서다.
운영 및 계속 사용 중인 QA 주소가 새 공개판을 제공할 수 있는지도 확인해, 공유 DB만 앞서가는 상태를 만들지 않는다.

새 판본에 문제가 있으면 기본 공개 포인터를 이전 발행판으로 복원한다. 새 판본 파일·발행 기록과 그 판본에서 만든 학습 기록은 삭제하지 않는다.
코드 복원까지 필요하면 모든 발행 판본과 저장 계약을 지원하는 호환 배포를 사용한다. 단순히 오래된 코드로 되돌리는 것을 복구로 간주하지 않는다.
브라우저 답안은 판본별이며 서버 단어/SRS와 다르다. 기존 학습자의 구판 접근·이어보기를 보존하고 무단 답안 이식/판본 강제 전환을 하지 않는다.

## 출시 후 개선과 자동화의 종료 규칙

- 첫 출시 전에는 위 출시 조건을 해소하는 승인된 작업 하나만 고른다. ‘더 좋아질 여지’는 후속 목록에 기록한다.
- 착수마다 새 작업이 어떤 출시 장애를 닫는지, 완료 증거가 무엇인지 설명할 수 있어야 한다. 조건을 충족하면 후보 확장을 끝낸다.
- 접근/승인 대기 때문에 막혔다고 일반 문항 추가·도구 보완으로 우회하지 않는다. 다른 독립적인 출시 필수 작업이 없으면 대기한다.
- 마지막 실제 사용자 응답 후30분·중단/대기/설계 지시·중복 실행 방지·변함없을 때 조용히 대기하는 기존 예약 규칙을 유지한다.
- 출시 뒤에는 저장/권한/학습 중단·의미 오류를 우선한다. 긴급 오류는 빠르게 처리하고 일반 개선은 묶어 발행한다. 잦은 판본 증식을 피한다.
- 실제 사용의 기록/제보와 기존 로그·보드로 판단한다. 이를 위해 새 분석 플랫폼이나 관리 체계를 만들지 않는다.
- 매 과제는 최종 후보 재검수 → 기대/실제·반례·한계 리뷰 → 다음 방향 또는 대기 결정으로 끝낸다.
  구현·자동검수·실계정·운영 반영·판본 발행은 별도로 보고한다. 작업/문항/테스트 수를 품질 점수로 만들지 않는다.
- 같은 대상/범위의 유효한 승인은 재사용한다. 새로운 운영 변경은 승인 범위를 확인하며, 자동 승인 검토가 차단한 동작을 새 승인 없이 재시도/우회하지 않는다.
