# 서재 과 추가·숫자 정렬 — 구현·검수

2026-09-30 KST. 오너가 「담긴 글 보기에서 임의 순서로 추가하되 과 순서 유지」 설계에 이어 구현·즉시 병합을 승인했다. 기존 원본/학습 기록을 보존하는 범위다.

## 범위와 사용자 변화

내 서재의 소유한 책에서 목차를 펼치면 `+ 과 추가`를 제공한다. 과 번호·선택 제목·본문을 입력하고 같은 화면으로 돌아온다. 8→3→5과로 추가해도 3→5→8과로 표시한다. 번호가 비어 있어도 허용하며 자동으로 당기거나 연속 번호로 바꾸지 않는다. 여러 과로 나누기는 기존 문장/이중 언어 분할기를 재사용하고 저장 전에 번호를 각각 수정할 수 있다.

기존 과의 `··· → 과 번호 수정`은 기존 material ID를 유지한다. 공개 교재 판본과 PDF 페이지에는 이 편집을 노출하지 않는다. 문구·장식은 기존 서재 UI를 따르고 별도 등록 화면 이동을 줄인다. 순서가 비어 있을 수 있으므로 뷰어의 총수는 「N과까지」가 아니라 「N과가 담겨 있어요」로 표시한다.

## 저장 계약

- 기존 `reading_materials.processed_json.metadata.book.order`가 정본이다. 새 표·외부 패키지·메뉴 체계를 추가하지 않는다.
- 소유자 RPC가 숫자 정렬/20개 단위 목록, 추가, 조건부 번호 변경을 맡는다. 같은 번호를 덮어쓰지 않으며 충돌 시 기존 과를 열 수 있다. 한 배치 중 충돌하면 전체를 취소한다.
- 기존 서재 관리와 같은 소유자 transaction advisory lock을 써 과 추가/번호 수정과 휴지통/복원의 충돌을 직렬화한다. 익명·타 계정·휴지통의 책에 쓰기를 허용하지 않는다. RLS와 invoker 권한을 유지한다.
- 새 과는 비공개·미분석 상태로 추가한다. 소유한 책의 언어/난이도를 이어받는다. 새 자료를 추가하면서 자동 AI 분석을 호출하지 않는다.
- 책별 IndexedDB 초안과 Web Locks를 재사용한다. 저장 요청 ID와 입력을 먼저 고정하며 응답 유실 뒤 새로고침해도 같은 요청으로 결과를 확인한다. 지원하지 않는 브라우저에서 보호 장치를 조용히 생략하지 않는다.
- 예전 이어 적기 입구도 동일 RPC를 사용한다. 새 책 최초 생성은 기존 경로를 유지한다.
- 번호 수정은 잠근 행의 번호와 자동 생성 제목만 바꾼다. 본문·번역·사전·material ID·진도·단어·FSRS를 재생성하지 않는다.
- 실제 반례: 과 번호 수정 이후 늦게 도착한 분석 snapshot이 옛 번호를 덮어썼다. 새로 관리한 과에만 `orderRevision`을 두고 trigger에서 최신 `book`/재시도 영수증 `bookEntry`를 보존한다. 새 분석 결과는 받아들이며 과 번호 RPC만 이 메타데이터를 갱신한다. 기존 모든 책을 일괄 변환하지 않는다.

## 검수와 한계

- PostgreSQL(PGlite): 역순 추가, 빈 번호, 숫자 페이지 경계, 배치 원자성, 같은 요청 재전송, 변경된 요청 거절, 번호 CAS/충돌, 늦은 분석 이후 번호/재시도 보존, 휴지통/타 계정/익명 거절, 기존 본문/학습 기록 보존 PASS. 이 검사를 기존 CI에 포함한다.
- 첫 전체 단위 검사: 412파일 / 4,354개 PASS. 이후 최종 후보의 필수 CI와 변경 영향 검사를 별도로 확인한다.
- 첫 프로덕션 빌드 PASS(컴파일 15.1분). 새 CSS 호환 경고와 이전 이어 적기의 RPC 오류 안내를 정리한 `bf9bdf6e7f4740dcc239f29169a1367c2b139b58`의 필수 CI 두 항목(프로덕션 빌드 포함) PASS. 이후 중복 로컬 재빌드는 자원 사용 증가로 중단했으며 성공으로 계산하지 않는다. 로컬 최종 UI 확인은 개발 서버에서 수행하고 최종 커밋의 프로덕션 빌드는 CI에서 확인한다.
- 실제 앱+합성 계정 브라우저 3흐름 PASS: 역순 입력/숫자 정렬, 중복 번호 거절, 번호 수정/재접속/정확한 다음 과 이동, 응답 유실→새로고침→동일 요청 복구, 여러 과 나누기/각 번호 변경. 기존 폴더·선택·휴지통·복원 회귀 3흐름도 PASS.
- 320/390/768/1280px 가로 넘침 없음, 추가/번호 수정 대화상자 Escape 초점 복귀, 실행 오류 없음. 데스크톱/320px 화면을 직접 확인했다.
- 개발 서버에서 추가 반례를 확인했다. Strict Mode가 dialog를 다시 연 뒤 이전 `close` 이벤트가 도착해 새 창을 닫았고, 초안 잠금도 이전 effect가 해제되기 전에 재요청되어 자기 자신을 다른 창으로 오인했다. 열린 dialog에는 늦은 close 이벤트를 적용하지 않고, 같은 인스턴스의 이전 잠금 해제 후 재요청하도록 교정했다. 다른 탭의 잠금 거절은 유지한다.
- 비연속 번호와 기존 이어 등록도 함께 확인한다. 1·8과가 있는 책은 다음 번호 9과를 사용하고 「현재 2과」로 표시한다. 원래 자료의 번호를 당기거나 총수와 마지막 번호를 혼동하지 않는다.
- 최종 개발 서버 실행에서는 역순 입력/번호 수정/뷰어 이동, 배치 분할, 기존 이름·즐겨찾기·충돌/좁은 화면 3흐름이 통과했다. 나머지는 페이지 이동 지연(새 경로 컴파일 87.1초 포함)과 검사기의 두 「휴지통」 버튼 선택 충돌로 중단됐다. 검사기는 탐색 메뉴의 버튼을 지정하고 DOM 준비 뒤 실제 컨트롤을 확인하도록 정리했다. 같은 7흐름을 필수 CI의 프로덕션 빌드에 추가해 최종 판정을 받는다. 개발 서버 중단을 성공으로 덮지 않는다.
- 최종 빌드·실계정·운영 적용은 아래 마무리에서 각각 기록한다. 합성 계정 및 로컬 PostgreSQL 결과는 실제 계정/다중 DB 연결/물리 기기 검수가 아니다.
- 원본 영구 삭제, 기존 중복 과 번호의 자동 정리, 기존 자료 전체에 대한 강제 번호 제약은 포함하지 않는다. 오래된 배포의 직접 INSERT까지 현재 클라이언트와 같은 API 계약이라고 주장하지 않는다.

## 운영 순서와 승인

오너의 이 작업 구현·병합 승인은 유효하다. 새 DB 함수/trigger의 운영 적용은 CLAUDE.md의 별도 DB 승인 범위다. 최종 SQL과 UI 검수·PR을 준비한 뒤 그 구체 적용만 확인한다. 환경 변수·원고·발행 판본은 변경하지 않는다. DB 적용 확인 → 검수한 head 병합 → 실제 운영 버전 및 계정 흐름 확인 순서다.

이전 PR #1327의 운영 migration 이력 불일치 세 건은 그대로 보존한다. 이 작업에서 이력을 삭제하거나 번호를 고치지 않는다. 이미 적용된 이력과 일치하도록 로컬 새 SQL 파일명을 정리할 필요가 있으면 내용 해시를 비교한다.
