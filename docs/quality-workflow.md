# 검수 실행·결과 기록·병렬 작업 제안

2026-09-17 · 승인한 자동화 1차. 대상은 #1321의 수업·개인 노트 출시 후보다.
이 문서는 도구 사용법과 분담 제안이다. 권한의 정본은 AGENTS.md·CLAUDE.md와 사용자의 명시 승인이다.
2026-09-17 별도 승인된 규약 정정은 웹 Node24/월드 Node22·월드 규칙 적용 범위·직접 요청과
제한적 Cloud 발주 구분이다. 운영 병합·DB·환경 변수의 별도 승인과 데이터 보호는 유지한다.

## 실행

독립 checkout에서 현재 package.json과 같은 Node24 및 `npm ci`, 최초 한 번
`npm run qa:browsers`로 준비한다. CI Linux는
`node node_modules/playwright-core/cli.js install --with-deps chromium webkit`을 쓴다.
Next/Vite가 읽는 실제 `.env` 환경 파일이 있는 checkout에서는 실행을 거절한다.
내용은 읽지 않으며 저장소의 `.env.example`은 실행 환경 파일로 취급하지 않는다.

| 명령 | 필수 검사 |
|---|---|
| `npm run qa:sql` | 수업 원본 직접 단어 저장·설명판 저장의 실제 로컬 PostgreSQL/RLS |
| `npm run qa:reader` | Chromium/WebKit 뜻·독음 표시, 일본어 대응 품사/캐시/늦은 응답 |
| `npm run qa:notes` | 두 브라우저의 개인 필기→확인→단어 정리→복구/서재 복귀 |
| `npm run qa:classroom` | SQL + 두 브라우저의 교사 판·계정 저장·전체/부분 재사용·기간 조회·학생 직접 저장/복습/출처 |
| `npm run qa:release` | 위 전체 묶음 |

앱이 필요한 묶음은 합성 환경 빌드와 로컬 서버를 자동 준비한다. 실행 코드/의존성/검사
입력이 같은 빌드만 재사용한다. 서버 포트3137이 사용 중이면 다른 세션 서버를 재사용하지 않고
실패한다. 같은 기기의 이 앱 검수 묶음은 순차 실행한다. 컴포넌트용 Vite는 빈 포트를 배정한다.

기존 `QA_*` 선택 플래그는 통합 실행기에서 필수 값으로 고정한다. 계정 키·공급자 키는
하위 프로세스에 전달하지 않는다. PGlite와 Playwright 브라우저는 잠금된 의존성을 사용한다.

## 결과와 재개

`node scripts/qa-report.mjs`로 최근 요약을 볼 수 있다. CI에서는 같은 요약을 Actions 화면에 자동 게시한다.
`.qa/latest.json`이 최근 결과 위치를 안내한다. `.qa/runs/<실행>/`에 `summary.md`,
`result.json`, 단계별 로그/화면/세부 보고서가 남는다. 실패한 브라우저 흐름은 가능한 경우
`failure-trace.zip`을 남긴다. 브라우저·DB·서버 종료와 하위 프로세스 종료까지 통과해야 PASS다.
실행 도중 코드가 달라지거나 필수 그룹이 빠졌으면 완료로 판정하지 않는다.

`npm run qa:release -- --resume .qa/runs/<이전 실행>/result.json`으로 재개한다.
같은 입력 지문·변경되지 않은 세부 증거·정상 종료를 가진 독립 단계만 재사용한다.
실패/중단된 단계는 새로 실행한다. 강제 종료로 `.qa/run.lock`이 남으면 기록된 PID가
끝났는지 확인한 뒤 그 잠금 파일만 제거한다. 다른 세션의 실행을 종료하지 않는다.

기록은 합성 Auth/HTTP + 실제 UI/로컬 SQL 증거다. `realAccount`, `externalAiEvaluation`,
`physicalDevice`, `production`을 별도로 표시한다. 표시용 어휘60개·의미 보존24개를 실제
공급자 정확도로 합산하지 않는다. 프로필 통과는 전체 Vitest/CI/실계정/운영 출시를 대신하지 않는다.
실계정 증거는 이 합성 보고서 폴더에 넣지 않는다. CI 아티팩트는 합성 폴더만 7일 보관한다.
수집기는 보고서·화면·로그·trace만 `.qa/evidence/`로 옮기며 심볼릭 링크, node_modules,
생성 번들을 따라가지 않는다. 실패의 실제 원인과 정리 시간은 보고서·CI 로그에서 바로 확인한다.

현재 상태의 정본인 작업 보드·#150은 유지한다. 실행 사실은 생성한 보고서를 참조하며,
승인·운영 적용 사실은 실제 근거가 있을 때만 기록한다. 이 실행기는 배포·병합·운영 DB 쓰기를 하지 않는다.

## 최종 재검수 → 결과 리뷰 → 다음 방향 (2026-09-18)

사용자의 요청은 매 과제의 마지막을 재검수로 닫고, 결과와 남은 일을 검토해 다음 방향까지
정하는 것이다. 체크 수나 자체 점수를 올리는 것을 목표로 삼지 않는다. 이 절은 Codex·Claude의
승인된 구현과 기존 QA/인계에 공통 적용하며 다른 프로젝트 예약 작업의 설정은 바꾸지 않는다.

1. **착수할 때** 사용자 동선·완료 조건·담당 범위와 제외 범위를 작업 보드에 고정한다.
   마지막에 통과시키려고 필수 항목을 선택 항목으로 내리지 않는다. 범위 변경은 이유를 기록한다.
2. **최종 후보를 고정한다.** 구현/검수 수정/문서와 별도 보드 커밋까지 준비한다. 공개 push는
   가능하면 한 번으로 모은다. 깨끗한 checkout의 정확한 head와 입력 지문을 기록한다.
3. **수정 후 다시 확인한다.** 최초 실패 재현 사례, 핵심 동선, 저장·권한·복귀·오류 처리 등
   변경에 맞는 검사를 실행한다. UI 변경은 실제 화면/좁은 화면/키보드도 확인한다.
   앱을 바꿨다면 검수한 실행 커밋과 배포 ID를 확인한다. 코드/후보/증거가 달라지면 마무리
   기록은 무효다. 문서만 바뀐 경우에도 diff·기존 증거·적용 범위를 다시 확인한 뒤 재사용
   이유를 남긴다. 전체 검사를 디버깅 반복문으로 쓰지 않되 필수 CI는 생략하지 않는다.
4. **결과를 리뷰한다.** 요청한 문제의 전후 관찰, 가장 강한 반례/제한, 실제 해결·남은 문제,
   재발 방지할 점을 쓴다. 코드가 존재하는 것과 사용자의 일이 해결되는 것을 구분한다.
   합성 UI, 실제 로그인, 의미 감수, 물리 기기, 운영 반영, 사용자 수용은 각각 따로 적는다.
5. **다음 방향을 정한다.** 남은 문제와 개선 후보를 영향·재발 가능성·의존 조건·작업 범위로
   비교한다. 지금 1개를 우선 선정하고 이유와 완료 조건을 적는다. 로그인/오너 선택에 묶인
   항목은 의존 조건을 남기고, 독립적으로 가능한 승인 범위를 계속한다. 승인 범위 밖 제안은
   자동 착수하지 않는다. 새 입력/결함이 없으면 대기하며 무의미한 할 일을 만들어내지 않는다.
6. **이 기록을 끝으로 마무리한다.** `qa:closeout check`로 누락·오래된 후보·증거 변경을 검사한다.
   점검 뒤 다시 수정하면 최종 후보를 새로 고정하고 영향 범위만 재검수한다. 같은 head의
   CODEX_DONE은 한 번만 남긴다. 이 절차 자체의 개선도 같은 마무리를 거친다.

### 실행 가능한 마무리 기록

```sh
# 모든 최종 커밋이 끝난 뒤: 기존 기록을 덮어쓰지 않는다.
npm run qa:closeout -- init reader-focus-20260918
# 에이전트가 .qa/closeouts/reader-focus-20260918/review.json을 실제 근거로 채운다.
# 검수 로그 등은 같은 폴더나 기존 .qa/runs, .qa/live에 두고 SHA-256을 기록한다.
npm run qa:closeout -- check reader-focus-20260918
```

`review.json`의 핵심 항목:

- `scope`: 이번 과제의 완료 경계. 출시 후보 전체를 작은 수정 과제와 혼동하지 않는다.
- `candidate`: init이 기록한 head/입력 지문/고정 시각. 사후 수정으로 우회하지 말고 새 ID로 재고정한다.
- `checks[]`: id, 기대 동작, 필수 여부, 종류, passed/failed/not-run, 실제 관찰.
  실행한 검사에는 최종 확인 시각, fresh/verified-reuse, 증거의 상대 경로/sha256을 쓴다.
  재사용은 이전 로그를 새 실행처럼 쓰는 것이 아니다. `reuseReason`에 비교 범위·동일성 확인을 쓴다.
  미실행은 원인을 적는다. `kind`는 automated/synthetic-ui/actual-account/physical-device/editorial/inspection이다.
- `review`: outcome(전후 결과), counterevidence(반례·한계), learning(다음에 반영할 점), remaining(미해결 목록).
- `next`: candidates(할 일·이유·완료 조건·now/later/blocked·existing-scope/proposal/needs-user·의존 조건),
  selected(지금 할 일의 ID 또는 null), reason(선택/대기의 근거).

예를 들어 검사 하나는 다음 형태다. 실제 로그에서 계산한 해시를 넣어야 한다.

```json
{
  "id": "keyboard-return", "expectation": "조회 후에도 Escape로 선택 단어에 복귀",
  "required": true, "kind": "synthetic-ui", "status": "passed",
  "observed": "Chromium/WebKit에서 조회 완료 후 키보드 이동·복귀 확인",
  "method": "fresh", "checkedAt": "2026-09-18T15:00:00+09:00",
  "evidence": [{ "path": ".qa/runs/current/report.json", "sha256": "실제 64자리 해시" }]
}
```

결과는 같은 폴더의 result.json/summary.md에 저장한다. `reviewed`(exit0)는 **명시된 과제 범위의
리뷰 완료**, `follow-up`(exit2)는 필수 실패/미실행 또는 남은 문제가 있는 정직한 중간 인계다.
누락·변조·오래된 후보는 exit1이며 완료가 아니다. 고립된 PASS 하나가 전체 과제를 덮지 않는다.
기존 result.json을 그대로 신뢰하지 말고, 인계 직전에 항상 check를 새로 실행한다.
도구는 기록/파일 무결성을 검사할 뿐 관찰의 진실성·실제 번역 정확성·사용자 만족을 독립 인증하지 않는다.
공개 CI 게이트·병합/배포 승인과 별개다. 다음 작업을 실행하거나 DB/환경/알림/일정을 바꾸지 않는다.

`.qa/closeouts`는 합성 CI 아티팩트 수집 대상 밖이다. 개인 자료·Auth 상태·쿠키·토큰을
검수 증거로 저장하지 않는다. 공개 PR에는 비식별 결과 요약만 별도로 작성한다.
읽기 전용 검토라면 checkout을 고치지 않고 같은 리뷰 항목을 응답/허용된 검토 결과로 전달한다.

### 추가 개선과 중단 기준

- 사용자에게 같은 결함을 다시 지적받았거나 동일 실패가 반복되면 재실행만 하지 말고 원인을
  다시 검토한다. 최초 실패를 재현하는 검사 하나를 남긴다. 회고 문서를 매번 늘리지 말고
  기존 결과의 learning과 해당 회귀 검사를 갱신한다.
- UI 변경은 ‘교재 → 뜻 → 저장 → 복귀’처럼 실제 동선 하나를 초기/최종 검수의 기준으로 삼는다.
  보기 좋은 한 화면과 테스트 개수만으로 성공을 선언하지 않는다.
- 새 코드가 없고 동일 head/같은 입력을 이미 검수했다면 알림·PR 코멘트·전체 검사를 반복하지 않는다.
- 기본 개선 우선순위는 데이터/권한/저장 실패 → 핵심 학습 동선/의미 오류 → 접근성/기기 회귀 →
  표현 다듬기다. 기계적인 점수 순위 대신 실제 사용자 영향과 선행 조건으로 예외를 설명한다.
- 새 SaaS/스케줄러 대신 기존 Node 실행기·SHA 증거·Vitest를 재사용한다. 기존 QA 수단을 채택하고,
  ‘CI PASS=실사용 완료’ 해석은 배제했다. 별도 예약 자동화를 만드는 것은 이 변경에 포함하지 않는다.
- 다음 세 과제 뒤에 사용자 재지적·완료 후 재발·미검수 누락·중복 실행을 비교해 이 방식의
  유지/수정 여부를 판단한다. 관측하지 못한 횟수/시간/만족도는 0이나 성공으로 추정하지 않는다.

## CI

기존 lint/콘텐츠/Vitest와 조판·뷰어·smoke·학습 검사를 유지하고, 수업·노트·뜻 표시의
통합 묶음을 추가한다. 테스트 빌드는 지문이 같은 경우 두 번 만들지 않는다.
비교 범위 전체가 보드/검수 이력 Markdown만이면 경량 판정을 한다. PR은 base와 비교하므로
앱 변경을 담은 PR의 후속 문서 커밋은 여전히 전체 검사를 한다. 이전 head의 성공을 무검증으로
최신 head에 옮기지 않는다. 보드/구현 커밋을 분리한 채 한 번에 push하면 중복 실행을 줄일 수 있다.
커리큘럼/화면 규약/실행 코드/SQL/알 수 없는 변경은 전체 검사다. 필수 검사 이름은 유지하고
최종 판정은 선행 검사 중 실패·취소·누락이 있으면 통과하지 않는다.
CI는 전체 묶음이 통과한 직후 같은 입력으로 재개하여 10개 단계가 모두 검증된 증거를 재사용하는지도 확인한다.

## 병렬 세션 분담 제안: 우선 3개

| 역할 | 제안 담당 | 경계 |
|---|---|---|
| 통합·품질(현재 세션) | 검수 실행기/CI·출시 후보·최종 통합 | 공통 파일 조율, 운영 변경은 기존 승인 규칙에 따라 순차 처리 |
| 교재 | 한 언어·한 레벨 원고/커리큘럼·근거·문항·정답 | 공통 뷰어/디자인 토큰/판본 발행기 변경은 먼저 협의 |
| 제품 기능 | 뷰어·수업·개인 노트 중 한 묶음과 전용 코드/테스트 | 같은 파일을 여러 세션에 배정하지 않고 공통 저장/RPC는 담당 조율 |

착수 카드: 목적, 기준 커밋, 포함/제외 파일, 사용자 동선, 완료 조건, 검사 명령, 산출물 PR,
공유 계약. 별도 작업 공간을 사용하고 변경 중인 iCloud checkout에서 브랜치를 전환하지 않는다.
각 세션은 자체 검수와 근거를 완성해 인계한다. 통합 단계에서 처음 검수하지 않는다.

새 세션을 실제로 배정할 때 아래 빈칸을 채워 전달한다. 이것은 권한 부여가 아니라 작업 경계 기록이다.

```text
목적과 사용자 동선:
기준 PR / 정확한 40자 커밋:
배정받은 브랜치 네임스페이스 / 별도 작업 공간:
수정 담당 파일:
다른 세션이 담당하는 파일과 필요한 계약:
포함 / 제외 범위:
완료 조건:
실행할 QA 프로필 / 추가 검수:
실계정·물리 기기 등 미실행 조건:
인계 PR / 생성 보고서 / 남은 결정:
```

교재 세션은 첫 작업을 한 언어·한 레벨의 커버리지와 한 단원으로 제한하는 편이 좋다.
기존 발행판 ID·42과 구성·표현 출처를 확인하고, 원고 수정과 발행판 교체를 따로 판정한다.
제품 세션은 뷰어·수업·노트 전체를 동시에 맡기기보다 한 사용자 동선으로 범위를 정한다.
공통 파일 변경이 필요하면 구현 전에 통합 담당에게 범위와 계약을 전달한다.

보드의 Codex-5 교재 순회에는 과거 발주가 남아 있으므로 최신 작업/PR/판본을 확인한 뒤
새 범위를 배정해야 한다. 구 lessons 원고와 발행된42과 책을 혼동하지 않는다.
이번에는 별도 세션을 만들거나 기존 담당의 소유권을 변경하지 않았다.

## 남은 단계

- 공개 배포 사전 검사 `npm run qa:live -- --deployment <개별 배포 origin> --commit <검수한 40자 실행 SHA> --stable <고정 origin>`를 추가했다.
  별도 검수한 실행 SHA를 입력해야 하며 서버 응답에서 기대값을 가져오지 않는다. 버전/판본/no-store·
  로그인 화면·코드 없는 callback의 내부 복귀·외부 경로 거절·검사 도중 배포 변경을 확인한다.
  고정 주소는 같은 커밋뿐 아니라 같은 deploymentId여야 PASS다. 운영 환경은 이 Preview 검사에서 거절한다.
  공개 정보만 `.qa/live/`에 남기며 합성 CI 증거와 섞지 않는다. 실제 인증 성공·OAuth 허용 목록을 확인하는 도구는 아니다.
- 고정 검수 주소와 정상 인증의 교사/학생 전용 계정: 실제 불일치를 확인했으며 연결 변경은 아직 실행하지 않았다.
  구체적 연결안·정상 인증 문맥 분리·한 번의 실사용 검수 순서는 `docs/qa-live-workflow.md`에 정리했다.
- 승인 화면 기준 이미지 비교·접근성 검사: 기존 화면·기하 사례를 기준으로 선정. 물리 Pencil 검수는 별도.
- 실제 모델 의미 평가: 기준 답 교정 후 공급자/프롬프트 버전·비용 한도를 정해 실행. 현재 합성 응답과 구분.
- 교재 커버리지·한자 도입·문항/정답 연결: 기존 lint/판본 도구 확장. PDF·음성 보류 유지.
- 규약 정합화: 별도 승인안에 대한 오너의 “승인. 다음 작업 진행” 후 두 파일에 반영했다.
  이전 자동 승인 검토의 보류는 해소됐으며, 런타임·병합·DB·환경 변수 권한을 추가로 변경하지 않았다.

기존 PGlite(Apache-2.0)·Playwright(Apache-2.0)를 재사용했다. 새로운 SaaS·대시보드·예약 자동화는 추가하지 않았다.
