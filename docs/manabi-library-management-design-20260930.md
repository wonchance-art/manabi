## 1. 목표와 첫 제공 범위

최신 디자인 지시: 목록과 짧은 동작명 중심. 상시 설명·홍보 문구·장식용 표식은 줄이고, 삭제 결과·오류·선택 수·접근성 이름은 남긴다. 자료와 폴더의 정리는 같은 화면에서 수행한다.

자료를 선택해 정리하고, 잘못 제거한 자료를 되찾은 뒤, 읽던 위치에서 계속 배울 수 있게 한다. Study와 Play는 같은 원본·개인 보관 관계·학습 출처를 사용한다. 서재 보관은 과정 등록이나 학습 완료를 뜻하지 않는다.

- 첫 제공: 다중 선택, 현재 목록 전체 선택, 폴더/하위 폴더, 폴더 추가·이동·이름 변경, 개인 표시 이름, 즐겨찾기, 검색/필터, 휴지통/복원, 항목별 실패·재시도, 실행 취소, 모바일/키보드.
- 원본 영구 삭제는 휴지통과 별도 구현 묶음이다. 참조와 파일 삭제 계약을 검증한 자료 종류부터 제공한다. 시안의 영구 삭제 버튼은 흐름 제안이며 모든 소유 자료의 즉시 삭제를 구현 승인한 것이 아니다.
- 여러 파일 가져오기, 원본 다운로드/자료 목록 내보내기는 기존 입력·다운로드 경로를 재사용하는 후속 묶음. 새 PDF 조판·변환 기능이 아니다.
- 태그/스마트 폴더·AI 자동 분류·공유 폴더·외부 앱 동기화·새 관리 대시보드·예약은 이번 범위에 추가하지 않는다.

## 3. 사용자 동작 계약

| 동작 | 변경 | 변경하지 않는 것 |
|---|---|---|
| 폴더에 추가 | 소속 관계 추가 | 원본·다른 폴더·학습 기록 |
| 폴더 안에서 이동 | 현재 폴더 소속 제거 + 목적지 추가를 한 항목의 원자적 작업으로 처리 | 다른 폴더 소속 |
| 전체/검색 화면에서 정리 | 폴더 추가 또는 소속 관리 | 출발 폴더를 추정해 모두 제거하지 않음 |
| 이 폴더에서 빼기 | 지정 소속만 제거 | 보관 상태·원본 |
| 폴더만 삭제 | 폴더와 하위 폴더 구조를 비활성화 | 자료 자체. 활성 폴더 소속이 없으면 미분류 |
| 휴지통으로 이동 | 본인의 전체·최근·즐겨찾기·폴더 목록에서 제외 | 원본·공개 상태·읽기 위치·단어·SRS·답안 |
| 복원 | 본인의 보관 상태 활성화, 존속하는 폴더 소속 복원 | 새 업로드/새 학습으로 계산하지 않음 |
| 이름 변경 | 서재의 개인 표시 이름 변경 | 원본 제목·공개 제목·학습 출처 식별자 |
| 원본 제목 편집 | 기존 소유자 편집기로 명시 진입 | 개인 이름 변경과 섞지 않음 |

기본 ‘이름 변경’을 소유 여부와 무관하게 개인 표시 이름으로 통일한다. 앞선 시안에서 소유 자료는 원본 제목을 바꿀 수 있도록 남겨 둔 모호성을 좁혔다. ‘원래 이름 사용’으로 별칭을 지울 수 있고 검색은 별칭·원래 제목·파일명을 함께 사용한다.

폴더 화면은 해당 폴더에 직접 담은 자료를 기본으로 보여준다. 하위 폴더 자료를 합산해 이미 보이는 자료를 다시 세지 않는다. 폴더 트리와 경로로 하위 폴더에 이동한다. 자동으로 모든 언어 폴더를 만들거나 Study/Play별 복사본을 만들지 않는다.

휴지통 자료를 복습의 출처 링크에서 여는 것은 가능할 수 있지만 복원은 별도 명시 동작이다. 원본 접근 권한이 사라졌다면 내용을 보여주지 않는다. 열람 이력이 늦게 도착해도 휴지통 상태를 되돌리지 않는다.

## 4. 식별자와 보존 경계

- 보관 키는 `(owner_id, target_kind, target_id)`다. `owner_id`는 로그인 사용자에서 서버가 얻는다.
- `material`은 기존 composer 정본으로 정규화한다. 학습 사본을 별도 원본처럼 중복 선택하지 않는다.
- `pdf`는 소유 PDF와 연결된 페이지/발췌의 기존 그룹이다. `book`은 기존 소유 책 그룹 키다. 둘 다 서재에서 한 항목으로 정리한다.
- `edition`은 발행 판본의 정확한 ID다. 동일 제목의 신·구판을 병합하지 않는다. 다언어 확장 시 book ID까지 포함하는 식별 계약은 별도 전환으로 다룬다.
- folder/title/star/trash 작업은 reading material 본문·document JSON·첨부 해시·원본 제목·publication pointer·읽기 위치·단어 뜻·SRS에 DML을 하지 않는다.
- 원본 노트 필기·인식 후보·개인 교정과 브라우저 답안은 각각 기존 정본에 둔다. 새 관리 테이블에 복제하지 않는다.

## 5. 저장 모델 제안

이 절의 이름은 구현 명세이며 아직 생성한 테이블/마이그레이션이 아니다.

| 구성 | 필드/역할 | 이전 방식 |
|---|---|---|
| 기존 `library_collections` 확장 | `parent_id`, `revision`, `deleted_at`, 폴더 삭제 작업 식별자 | 기존 행은 루트 폴더. 이름·ID·created_at 유지 |
| 기존 `library_collection_items` | 자료의 복수 폴더 소속 | 기존 PK와 관계 유지. 비활성 폴더의 소속은 목록에서 제외 |
| 새 `library_item_state` | 원본 키, `state(active/trashed/removed)`, `display_title`, `favorite`, `revision`, 서버 변경 시각 | 행이 없으면 기존 노출 계약 적용. 처음 개인 설정/정리할 때 생성 |
| 비공개 작업 헤더 | 사용자, 요청 UUID, 동작·입력 해시, 대상 수, 상태, 만료 시각 | 일괄 선택 고정과 응답 유실 복구용 |
| 비공개 작업 항목 | 정규화된 대상 키, 예상 revision, 항목별 결과, 작업 전후의 최소 개인 메타데이터 | 재시도·조건부 실행 취소용. 원문/파일/비밀 경로 저장 금지 |

`removed`는 타인 공개 자료의 보관 기록 영구 제거 후 자동 재등장을 막는 최소 상태다. 휴지통에도 표시하지 않으며 명시적인 ‘다시 담기’로만 활성화한다. 단순히 이 행을 지우면 과거 열람 이력에서 자료가 살아날 수 있으므로, 최소 식별자와 상태는 남긴다. 이 상태를 원본 영구 삭제 완료로 사용하지 않는다.

휴지통 이동은 소속 행을 바로 삭제하지 않는다. 활성 목록에서 상태를 걸러내고 복원 시 여전히 존재하는 폴더만 연결한다. 휴지통 체류 중 폴더가 지워져도 자료는 미분류로 복원할 수 있다. 파일이 남아 있는 휴지통 이동은 저장 공간을 비우지 않는다. 자동 영구 삭제는 하지 않는다.

폴더 부모는 `(owner_id,parent_id)` 복합 참조로 같은 사용자의 폴더만 허용한다. 자기 자신/자손으로 이동 금지. 트리 변경은 사용자별 트리 잠금과 서버 순환 검사로 경쟁 상태를 막는다. 기존 중복 모음집 이름은 임의 병합/변경하지 않는다. 새 생성·이름 변경만 같은 부모 아래 중복을 거절하고, 기존 중복은 경로·생성 시각으로 구분한다. 기존 데이터를 정리하지 않고 UNIQUE 인덱스를 곧바로 추가하지 않는다.

## 6. 조회와 쓰기 인터페이스

조회는 기존 카탈로그의 권한·그룹 정규화 위에 개인 상태를 적용한다. 새 별도 원본 목록 엔진을 만들지 않는다.

- v2 조회 계약: 현재 폴더/검색/종류/언어/읽기 상태/즐겨찾기/휴지통/정렬, 페이지와 `total`, 항목의 `revision`·허용 동작을 반환한다. 함수 버전은 명시적으로 나누어 기존 default 인자 오버로드 충돌을 피한다.
- 기존 `personal_library_page`도 같은 상태 필터를 사용하도록 호환한다. 전체 목록뿐 아니라 `p_recent`, 총수, 미분류, 자식 목록과 저장 버튼 상태까지 같은 기준이다.
- 기본 제목 정렬은 개인 표시 이름 우선. 원본의 created_at을 개인 정리 시간으로 덮어쓰지 않는다. 마지막 열람은 기존 정상 렌더 기록을 따른다.
- 접근 불가 자료는 원문/발췌/파일 경로 없이 ‘접근할 수 없는 자료’로 구분해 정리할 수 있게 한다. 이전에 접근 가능했다는 이유로 현재 비공개 내용을 재노출하지 않는다.

제안 작업 계약:

1. `prepare`: 명시 키 배열 또는 검증한 필터로 대상 manifest를 서버에서 고정한다. 정규화·중복 제거·권한 검사 후 정확한 수와 제한 사유를 돌려준다.
2. `apply`: manifest의 동작과 목적지를 변경 없이 실행한다. 매 항목의 현재 권한·revision을 다시 확인한다.
3. `status`: 응답이 유실됐을 때 같은 요청 결과를 조회한다. 새 UUID로 중복 작업을 만들지 않는다.
4. `retry`: 미완료 항목만 재검증한다. 권한 상실/동시 변경은 단순 통신 재시도와 구분한다.
5. `undo`: 이 작업이 바꾼 개인 상태·소속만 되돌린다. 이후 변경이 있으면 해당 항목은 충돌로 남긴다.

같은 요청 UUID에 다른 입력이 오면 충돌이다. 작업 전체가 한 번에 원자적이라고 표시하지 않는다. 한 자료의 이동/휴지통/복원은 원자적이고, 묶음은 `성공/이미 적용/충돌/접근 불가/미완료`를 구분한다. 예상 실패는 항목 단위로 처리하고, 호출 자체가 끊겨 커밋 여부가 불명확하면 status로 확인한다.

초기 처리값 제안은 호출당 100개, 한 manifest 최대 5,000개다. 로컬 실제 SQL·응답 크기·실행 시간 검수 후 낮출 수 있다. 한도를 넘으면 정확한 사유와 나눠 처리하기를 제시하며 ‘전체 선택’으로 표시한 뒤 몰래 일부만 처리하지 않는다. 준비 후 미실행 작업은 30분, 실행 결과는 7일 보관을 초기값으로 검토한다. 만료 후에는 재선택을 요구한다. 유효기간은 사용자 자료의 수명과 무관하다. 새 스케줄러 없이 만료 판정과 제한된 정리를 기존 요청 경로에서 처리하는 범위를 우선한다.

실행 취소는 시안의 전체 배열 스냅샷 복원 코드를 제품으로 이식하지 않는다. 다른 탭의 새 폴더·새 보관·이후 수정까지 되돌릴 수 있기 때문이다. 항목별 작업 후 revision이 일치할 때만 최소 변경을 역적용한다. 삭제한 폴더 구조를 되돌릴 때 새 동명 폴더가 있으면 덮어쓰지 않고 충돌을 안내한다.

## 7. 다중 선택과 재접속

- 현재 표시된 행 선택과 서버 검색 결과 전체 선택은 다른 상태다. 전체 선택 시 manifest 생성 시각의 대상만 고정하며 이후 유입된 자료는 포함하지 않는다.
- 필터/폴더/계정이 바뀌면 선택을 해제하고 알린다. 정렬·더 보기에서는 같은 키 선택을 유지한다. 키보드 전체 선택은 목록에 초점이 있을 때만 동작한다.
- 적용 전 선택 취소는 아무것도 쓰지 않는다. 적용 도중 중단은 아직 실행하지 않은 항목만 멈추며 이미 완료한 작업을 자동 취소하지 않는다.
- 네트워크 오류 시 실패 자료만 선택 상태로 남긴다. 재접속 시 기존 요청 상태를 확인하고 계속할지 보여준다. 별도 작업 대시보드는 만들지 않는다.
- 일괄 쓰기는 온라인에서 확인한 권한과 상태로 수행한다. 오프라인에 파괴적 작업을 쌓았다가 로그인 직후 자동 실행하지 않는다.
- 다른 탭/기기에서 변경한 항목의 revision 불일치는 자동 덮어쓰기하지 않는다. 새 상태를 확인하고 다시 선택한다.
- 성공 후 `personal-library`, `library-recent`, 폴더/개수, 관련 `library-bookmark`, 자료 정보 캐시를 사용자 범위로 갱신한다. SRS 캐시는 정리 작업 때문에 초기화하지 않는다.
- 원문에서 서재로 돌아오면 기존 `returnTo`와 필터·목록 위치를 복원한다. 삭제로 행이 사라지면 가장 가까운 남은 행 또는 목록 제목에 초점을 둔다.

## 8. 권한 계약과 호환 경로

폴더는 개인 분류다. 폴더 소속이 열람권·편집권·교사/관리자 권한을 부여하지 않는다. 작업 준비와 실제 적용 모두 세션 소유자와 현재 원본 권한을 검사한다. 클라이언트가 보낸 owner/권한 플래그는 신뢰하지 않는다.

공개 API 테이블에는 RLS와 명시적 GRANT를 함께 설계한다. 함수는 `security invoker`와 고정 search_path를 기본으로 한다. 사용자별 SELECT/INSERT/UPDATE/DELETE 경계 및 owner 변경 금지를 독립적으로 검수한다. 원본 접근 불가여도 이미 본인에게 속한 보관 관계를 정리할 수 있어야 한다.

작업 헤더/manifest는 Data API에 노출하지 않는 비공개 스키마와 사용자 RLS를 제안한다. invoker 함수에 필요한 최소 스키마/테이블 권한을 부여하되, 공개 REST로 작업 결과나 manifest를 임의 작성할 수 있는 구조는 피한다. ‘테이블 쓰기를 막았는데 invoker RPC만 자동으로 쓸 수 있다’는 잘못된 가정을 하지 않는다. 기존 공개 테이블의 직접 쓰기가 남는 동안은 불변식을 서버 제약/트리거에서도 검사해야 한다. 이 범위에서 관리자 우회·service role 브라우저 사용은 없다.

호환 대상:

| 경로 | 처리 |
|---|---|
| `LibraryShelf` 메뉴 | 같은 작업 API로 단일·일괄 동작 통합 |
| `LibraryCollections` | 기존 ID/다중 소속을 유지하며 트리·폴더 이름으로 전환 |
| `LibrarySaveButton` | 담기/해제/휴지통 상태를 공통 계약으로 처리. 휴지통이면 ‘복원해 담기’로 명시 |
| `/materials?tools=1&view=owned` | 기존 도구의 편집 등은 유지. 삭제는 새 휴지통 경로로 연결하고 휴지통 항목 중복 노출 방지 |
| 원문·학습 사본·PDF·교재 reader | 기존 ID/판본/위치 사용. 휴지통 출처 열람이 자동 복원하지 않음 |
| 과거 Preview/열린 탭 | 오래된 직접 DELETE가 안전한 새 삭제 계약을 우회하지 못하도록 출시 시점에 서버 차단 검수 |

오래된 DELETE를 차단하기 전 원본/첨부 교체·취소한 업로드·초안 정리 등 모든 삭제 호출부를 분류해야 한다. 정당한 임시 파일 정리까지 무작정 막지 않는다. 허용된 서버 삭제 경로와 상태 검증으로 분리하며, 오래된 앱에는 명확한 재접속 오류를 반환한다. 제품 버튼만 바꾼 상태를 삭제 보호 완료로 보고하지 않는다.

## 9. 원본 영구 삭제의 별도 완료 조건

휴지통은 목록 정리 기능으로 먼저 완결할 수 있다. 영구 삭제는 저장 공간과 참조 정리를 포함하는 후속이며, 아래 조건 전에는 실서비스에 활성 버튼을 노출하지 않는다. 사용자는 해당 단계에서도 휴지통 이동/복원을 사용할 수 있다.

- 공개 교재 판본, 타인 원본, 현재 공유/수업에서 참조하는 원본은 일반 영구 삭제 대상에서 제외한다. 원본 공개/공유 설정을 뒤에서 바꾸지 않는다.
- 직접 소유한 비공개 자료라도 본문·composer 사본·PDF 발췌·그룹 구성원·필기/교정/단어 출처·Storage 참조를 서버에서 대조한다. 각 종류의 삭제 범위가 증명된 어댑터만 허용한다.
- 기존 PK 행을 곧바로 DELETE해 CASCADE를 발생시키지 않는다. 학습 기록 참조가 있으면 원본 내용 제거 후 최소 삭제 표식으로 남기는 방법을 우선 검토한다. 학습 기록에 보존하는 발췌/개인 뜻과 삭제하는 원문 내용의 경계를 명시한다.
- 원문 내용을 남겨놓고 ‘영구 삭제’라고 표시하지 않는다. 파일/본문/학습용 파생 본문까지 완료했는지 별도로 확인한다. 서버·기기 캐시에서 오래된 내용이 다시 표시되지 않는지도 검수한다.
- DB와 파일 저장소가 하나의 트랜잭션이라는 가정은 금지한다. 검증한 삭제 계획 → 내용 접근/수정 중단 → 파일과 파생 자료 정리 → 완료 표식 순으로 재개 가능한 작업을 설계한다. 실패하면 ‘삭제 처리 미완료’이며 자동 복원이나 완료 처리를 하지 않는다.
- 작업 도중 연결이 끊겨도 서버의 완료/잔여 결과로 재개한다. 이후 재연결한 기기의 캐시 정리와 구형 클라이언트의 재업로드 방지까지 포함한다. 오프라인 기기에서 즉시 소거됐다고 주장하지 않는다.
- 타인 공개 자료의 ‘보관 기록 영구 제거’는 원본 삭제와 별개다. 이후 자동 재등장을 막는 최소 removed 상태를 남기며 실제 원본/다른 사람 기록은 보존한다.

이 단계의 정확한 FK/Storage 변경 파일 범위는 구현 전 전체 참조 조사로 확정한다. 이번 문서는 원본 삭제의 DB 마이그레이션을 승인하거나 적용한 것이 아니다.

## 10. 구현 묶음과 파일 경계

| 순서 | 구현 범위 | 끝났다고 판단할 근거 |
|---|---|---|
| A — 상태와 보존 | 개인 상태·폴더 부모/삭제 상태, 카탈로그 필터, 루트 정규화, 단일 휴지통/복원, 기존 저장 버튼/최근 조회 연결 | 격리 SQL에서 신구판·원본·단어/SRS·진도 해시 불변. 늦은 열람 기록 후에도 휴지통 유지 |
| B — 선택과 원자적 작업 | 고정 manifest·항목별 revision·이동/추가/실패 재시도/조건부 undo | 부분 성공·응답 유실·다른 탭 충돌·동시 폴더 이동 반례 통과 |
| C — 화면과 출시 후보 | 시안의 반응형 목록·폴더·선택 막대·휴지통, 기존 고급 도구 호환 및 오래된 쓰기 경로 보호 | 실제 앱 320px/키보드/긴 제목/재접속, 실제 계정 정리→복원→원문/복습 왕복 검수 |
| D — 원본 정리 | 영구 삭제 어댑터와 파일/파생 본문 정리 | 소유권·참조·부분 실패·캐시/구형 쓰기 검수 후 지원 종류별 활성화 |
| E — 입력 편의 | 여러 파일 추가 큐·중복 안내·다운로드/목록 내보내기·필요시 드래그 | 기존 composer 중복/초안/원본 보존 계약 유지 |

A/B/C를 첫 자료 관리 제공 묶음으로 묶는다. 내부 개발 순서와 사용자에게 중간 상태를 출시하는 것을 혼동하지 않는다. E의 드래그는 폴더 버튼 동작의 보조이고 필수 조작으로 만들지 않는다.

우선 코드 대상은 `src/lib/personalLibrary.js`, `libraryActivity.js`, `libraryReturn.js`와 기존 `src/components/library/*`, `src/components/web/LibraryPage.jsx`, `src/views/MaterialsPage.jsx`다. 필요한 분리는 `librarySelection`/`libraryOperations` 등 이 영역의 작은 모듈로 제한한다. 이름 변경은 개인 alias이므로 composer 본문 저장 경로를 건드리지 않는다. UI는 기존 `src/index.css` 토큰과 `docs/ui-conventions.md`를 따른다.

SQL은 새 마이그레이션으로 작성하되 적용 완료된 과거 파일을 수정하지 않는다. CLI로 이름을 생성하는 절차와 기존 격리 SQL 검증을 따른다. D의 source/Storage guard는 별도 영향표 없이 A 범위에 숨겨 넣지 않는다. A/B/C 출시를 위해 필요한 레거시 삭제 차단의 범위는 C에서 명시한다.

## 12. 도입과 복원

1. 최신 main 기준 격리 작업 공간에서 설계의 원본 키/삭제 호출부를 대조한다. 기존 iCloud 수정과 통합 후보를 보존한다.
2. 격리 데이터로 기존 ID/소속을 그대로 두는 추가형 마이그레이션과 기능 검수. 자동 자료 재분류나 본문 복사를 하지 않는다.
3. 검수 가능한 코드·SQL·이전/복원 절차를 준비한다. 새 DB 적용·Preview/운영 배포는 해당 대상과 변경 범위의 유효한 승인을 따르며 이번 설계를 포괄 운영 승인으로 해석하지 않는다.
4. 승인된 DB 계약을 확인한 뒤 그 계약을 지원하는 코드 배포. 미지원 스키마에서는 새 쓰기를 제공하지 않으며 기존 hard DELETE로 fallback하지 않는다.
5. 복원은 새 상태를 이해하는 호환 코드로 한다. 폴더/휴지통 상태를 무시하는 과거 배포로 즉시 되돌리지 않는다. 새 테이블을 내려서 ‘복원’하거나 새 사용자 정리를 유실시키지 않는다.
6. 기존 QA 주소·장시간 열린 탭·기존 저장 버튼의 동작까지 확인한다. 실제 계정 검수와 운영 반영을 코드/합성 검사 통과와 따로 기록한다.

## 14. 설계 마무리

- 기대: 시안의 선택·폴더·삭제를 기존 학습 데이터와 충돌 없이 구현할 순서와 계약을 정한다.
- 실제: 원본 복제 없는 개인 정리 계층, 휴지통 재등장 방지, 서버 선택 고정, 항목별 이동/재시도/undo, 기존 버튼·고급 도구·구형 클라이언트 연결과 A~E 완료 조건을 정리했다.
- 발견한 반례: 기존 원본 DELETE는 읽기 기록 CASCADE와 파일 정리 부분 실패를 일으킬 수 있다. UI 시안의 메모리 전체 스냅샷 undo는 다른 탭의 변경을 보존하지 못하므로 제품 구현에 사용하지 않는다.
- 시안 근거: 이전 단계에서 예시 자료 선택/전체 선택·폴더 추가/undo/생성·휴지통/복원·부분 실패 재시도·Shift 선택·즐겨찾기 해제를 브라우저에서 확인했다. 320/390/768/1100px의 5상태 가로 넘침·실행 오류 없음, 모바일 영구 삭제 확인과 다크 화면 확인. 이는 실제 저장/RLS/서버 경쟁 상태의 검수가 아니다.
- 이번 검수: 문서의 실제 경로·기존 함수·제약을 소스와 대조하고 문서/자기 보드 diff를 확인한다. 실행 코드 변경이 없어 제품 테스트를 다시 돌려 성공 건수를 만들지 않는다.
- 남음: 실제 SQL·성능 한도·동시성·역할별 권한·실계정·물리 기기·운영 반영·영구 삭제 참조 조사. 설계 완료를 제품 완성으로 계산하지 않는다.
- 다음 하나: **A의 개인 보관 상태와 단일 휴지통/복원 보존 계약을 격리 구현하는 것**. UI만 먼저 바꾸거나 원본 삭제를 확대하는 경로보다, 자료가 다시 나타나거나 학습 기록이 지워지는 문제를 먼저 막는다. 최신 main/기존 호출부 대조 후 범위 내 코드·격리 검수로 시작하며 외부 적용은 별도 승인 경계를 유지한다.
