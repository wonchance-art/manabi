## 0. 결론

1. **측정 없이는 켜지 않는다.** 서버 기능은 코드 상수(`ZH_SENSE_REVIEW = false`)로 꺼진 채 들어간다. 새 환경 변수는 승인 밖이라 쓰지 않는다. 측정 세트(조정용 40 + 보류 40)에서 기준(§3.5)을 넘을 때만 상수를 켜는 PR을 따로 낸다(AGENTS.md 공통 품질 원칙 「효과 있을 때만 켬」).
2. **호출 수 증가 0은 지금 구조에서 성립한다. 다만 후보가 있는 단어에만 그렇다.** 품사 판별은 요청당 Gemini light 1회다(`disambiguateZhPos.js:112-151`). 같은 프롬프트의 단어 줄에 「뜻 후보 ①②③」을 붙이고, 응답 항목에 `sense` 번호를 더한다. 그런데 이 호출은 **뜻 조회와 병렬**로 돈다(`analyze/route.js:164-207`). 그래서 사전에 아직 없는 단어(이번 요청에서 뜻을 처음 받는 단어)와 뜻 재조회 대상은 호출 시점에 후보가 없다. 그런 단어는 지금처럼 `pickZhMeaning`(품사 일치 → 첫 뜻)을 쓴다. 순서를 바꿔 직렬로 하면 미싱이 있는 요청의 대기 시간이 최대 15초 늘어서 하지 않는다.
3. **판별 대상은 지금 마크 집합 그대로 시작한다.** 지금 마크는 명·동·형 계열과 품사 미상만이다(`disambiguateZhPos.js:16-19,38-65`). 실측하면 예문의 한자 토큰 36,298개 중 51%(18,524)가 마크된다. 뜻이 여럿인 단어(refVocab `ko`에 `;`가 있는 것을 근사로 씀) 1,816개 중 67.6%(1,228)가 마크 안에 든다. 빠지는 588개는 전치사 212·양사 146·부사 56·접속사 54가 대부분이다. 마크를 넓히면 판별 단어 수가 늘어 프롬프트가 커지므로, 1차 측정에서 이 부류의 오답이 실제로 확인될 때만 넓힌다(§2.1).
4. **후보 밖 답은 버린다.** 모델은 후보 **번호**로만 답하고, 문구를 다시 쓰지 않는다. 번호가 범위 밖이거나, 정수가 아니거나, 그 단어에 후보가 없었으면 그 단어만 지금 동작으로 돌아간다. `sense: 0`(맞는 후보 없음)일 때만 `ctx`(10자 이내 한국어)를 받는다. `ctx`가 후보 중 하나와 정규화해서 같으면 그 후보로 바꾸고, 비거나 너무 길면 버린다. 이것은 지금의 `pos ∉ all이면 버림`(`:144`)과 같은 규칙을 뜻에 넓힌 것이다.
5. **「사전 등재」만으로 경계를 자동으로 바꾸면 안 된다는 것을 실측했다.** 예문 6,789문장에서 이웃 한자 토큰 둘을 이은 꼴이 표제어인 경우가 198번 나왔다. 그중 38번(19%)은 명백한 오병합이다: 一个人의 个+人 → 个人 23번, 他得了第一名의 得+了 → 得了 6번, 做完了의 完+了 → 完了 4번, 很多方面·很多云·很多媒体 4번, 打包带+走 1번. **이 꼴들은 모두 HSK 표(`zhHskLevel.json`)에 있다.** 97번(49%)은 생활 어휘의 구 표제어(交通卡+余额, 国际+转机)다. 그래서 자동 적용 조건을 「등재 **그리고** 이 문장에서 AI가 한 단어라고 판정」으로 둔다. 「AI 판단뿐」(등재 안 됨)이면 「한 단어로 묶을까요?」 후보로만 둔다. 이것이 정본 §8 문구의 실행 가능한 해석이다(§5).
6. **「등재」는 HSK 표 · `user_verified`/`jmdict` 행 · 코드 화이트리스트다. `source:'gemini'` 사전 행은 넣지 않는다.** 분석기는 사전에 없는 토큰마다 뜻을 받아 gemini 행으로 쌓는다(`fetchMeanings.js:274,301`). 우연 병합 토큰(笔在·这宗)도 그렇게 쌓였다(`disambiguateZhPos.js:45-46`). AD-R3로 사용자가 묶은 꼴도 그렇게 쌓인다. 이 행들을 등재로 치면 한 사람이 잘못 묶은 꼴이 모두의 자동 경계가 된다.
7. **지금도 AI 판단만으로 경계를 바꾸는 경로가 하나 있다.** OOV 「단어성 판정」의 분리 결과는 부분을 이으면 원 표기가 된다는 검사만 하고 자동 적용된다(`disambiguateZhPos.js:139-142,153-163`, `analyze/route.js:235-240`). 정본 §8을 따르면 이것도 「부분이 모두 등재(1글자 포함)일 때만 자동, 아니면 후보」로 바꿔야 한다. 다만 이는 출시된 동작을 바꾸는 일이라 측정 세트의 D 범주로 전후를 잰 뒤 결정한다(Q2).
8. **사용자 교정과 `user_verified`는 서버에서 판별하지 않고, 클라이언트 보존에서 이긴다.** 서버는 그 토큰이 사용자가 교정한 것인지 모른다. 교정값은 재분석 뒤 `preserveReanalysisTokens`가 덮는다(`reanalysisPreservation.js:24-30,53`). 그러니 교정된 토큰에서는 `meaningCheck`를 지우는 규칙 하나를 더한다. `user_verified` 행은 서버가 후보를 붙이지 않는다(오너가 확정한 첫 뜻을 그대로 쓴다). AD-R3로 묶은 토큰(`boundary` 표식)은 경계 후보에서도 뺀다.
9. **실패·시간 초과면 지금 결과 그대로다.** 판별기는 이미 모든 실패를 빈 결과로 수렴한다(`:116-118,147-150`). 뜻 선택은 그 결과에 얹히므로 따로 실패할 길이 없다. 응답 길이가 맞지 않으면 품사까지 통째로 버리는 지금 규칙도 그대로다.
10. **PR은 넷이다.** ① 측정 세트·채점기·실행 스크립트(제품 코드 0) → ② 서버 프롬프트·응답 처리(상수 꺼짐, 켜도 표시 0) → ③ 「뜻 확인 필요 N개」·카드 ⓘ·목록 교정 → ④ 경계 후보(묶을까요)와 등재 자동 묶기. ②의 상수를 켜는 일은 ① 측정 결과를 붙인 별도 PR이다(§10).

## 2. 측정(로컬, 호출 0)

### 2.1 판별 대상의 크기

refVocab 예문 6,789문장(중복 제거)을 지금 토크나이저와 `collectZhPosMarks`(빈 캐시 가정 — jieba 품사만 봄)에 넣었다.

| 항목 | 값 |
|---|---|
| 한자 토큰 | 36,298 |
| 마크되는 토큰 | 18,524(51.0%) |
| refVocab 표제어인 토큰 | 32,986(90.9%) |
| 뜻이 여럿인 토큰(refVocab `ko`에 `;` — 근사) | 1,816 |
| 그중 마크되는 것 | 1,228(67.6%) |
| 마크 밖 다의 토큰의 품사 | 전치사 212 · 양사 146 · 부사 56 · 접속사 54 · 대명사 31 · 조사 28 · 기타 61 |
| 8줄 문단(분석 요청 단위)당 마크 수 | 중앙값 22 · p95 30 · 최대 37(상한 120) |

- 근사의 한계: refVocab `ko`는 뜻을 `,`로도 나열한다(「매를 맞다, 얻어맞다」는 한 뜻). `;`만 세었으므로 다의어를 **적게** 센다. 운영 사전 행의 `meanings` 수는 운영 DB로만 알 수 있다(§3.3 스냅숏 SQL).
- 프롬프트 크기 추정: 마크당 후보 3개 × (뜻 약 8자 + 번호·품사 6자) ≈ 40자가 늘어난다. 문단당 마크 p95 30개면 약 1,200자다. 출력은 항목마다 `"sense":n` 약 6토큰이다. 지연 증가는 측정 세트 실행 때 잰다(미측정).

### 2.2 「등재만으로 묶기」의 오병합

같은 6,789문장에서 이웃 한자 토큰 둘(문장부호 제외)을 이은 꼴이 refVocab 표제어인 경우를 셌다.

| 분류 | 횟수 | 비율 | 예 |
|---|---|---|---|
| 전체 이웃 쌍 | 29,112 | — | — |
| 이은 꼴이 표제어 | 198 | 0.68% | — |
| 명백한 오병합 | 38 | 198 중 19% | 一个人 → 个人 ×23 · 他得了第一名 → 得了 ×6 · 做完了 → 完了 ×4 · 很多方面 ×2 · 很多云 · 很多媒体 · 打包带走 → 打包带 |
| 생활 어휘의 구 표제어 | 97 | 49% | 交通卡+余额 · 国际+转机 · 垃圾+分类 |
| 그 밖(대체로 맞는 묶음) | 63 | 32% | 不+客气 · 请+坐 · 那+时候 · 有+空儿 |

- 오병합 꼴(个人·得了·完了·多云·多媒体·多方面)은 **모두 HSK 표(`src/lib/data/zhHskLevel.json`, 10,935항)에 있다.** 「등재」 조건만으로는 막을 수 없다.
- 그래서 경계 자동 적용은 「등재 + 이 문장에서 AI가 한 단어라고 판정」 두 조건이 모두 필요하다. 같은 이유로 측정 세트 D 범주에 이 문장들을 넣는다.

### 3.2 사례 형식

```jsonc
{
  "id": "B03", "cat": "B", "split": "tune",            // tune(조정용) | holdout(보류)
  "sentence": "我给妈妈打了一个电话。",
  "word": "打", "line": 0,
  "candidates": [                                       // 운영 사전 행 스냅숏(§3.3)을 그대로 고정
    { "meaning": "때리다, 치다", "pos": "동사" },
    { "meaning": "(전화를) 걸다", "pos": "동사" },
    { "meaning": "(운동을) 하다", "pos": "동사" }
  ],
  "candidatesSource": "morpheme_dictionary@2026-10-xx",
  "accept": { "sense": [2] },                           // 맞는 후보 번호. 후보 밖 정답이면 "ctx": ["질투", "샘"]
  "forbidden": [ { "sense": 1, "why": "전화를 때리지 않는다" } ],
  "boundary": null,                                     // D 범주: { "pair": ["个","人"], "join": false }
  "why": "같은 품사 안의 다의어"
}
```

- `candidates`를 사례에 고정하는 이유: 운영 사전 행은 자가 치유로 바뀐다. 사례마다 후보를 고정해야 「현행 → 적용 후」를 같은 입력으로 비교할 수 있다.

### 3.5 재는 것과 출시 기준

| 기준선 | 방법 | 호출 |
|---|---|---|
| B0 현행(정답 품사 가정) | `pickZhMeaning(candidates, 정답 품사)`. 품사를 맞혀도 남는 오답(같은 품사 다의)의 하한이다 | 0(오프라인) |
| B1 현행(실제) | 지금 `buildZhPosPrompt` → 실제 pick → `pickZhMeaning` | 사례 묶음당 1 |
| N 적용 후 | 새 프롬프트 → `sense` 검증 → 선택 | 사례 묶음당 1 |

- 사례는 문단 단위(문장 4~8개)로 묶어 실제 요청처럼 보낸다. 마크 수와 지연도 함께 기록한다.

**켜는 기준(보류 세트 기준, 둘 다 만족)**
1. 치명 범주(B·D) FAIL이 B1보다 적고, D 범주의 오병합 자동 적용은 0건이다.
2. 전체 FAIL이 B1 대비 30% 이상 줄고, B1에서 PASS였던 사례가 N에서 FAIL로 바뀐 것이 1건 이하다.

추가로 지킬 것: 요청당 LLM 호출 수는 B1과 같다(`stats`로 확인). 판별 호출 p95 지연 증가는 1초 이하. REVIEW는 모두 사람이 판정하기 전에는 통과로 세지 않는다.

기준을 못 넘으면 상수를 켜지 않는다. 결과표와 원인을 보고하고 끝낸다.

### 4.1 단어 줄 — 후보가 붙는 조건

마크(지금 규칙 그대로) 중에서 다음을 모두 만족하면 「뜻 후보」를 붙인다.
- 캐시 행이 있고 `meanings`가 2개 이상이다(1개면 고를 것이 없다. 다만 E 범주 측정에서 1개짜리의 후보 밖 비율이 높으면 1개에도 붙인다 — Q3).
- 행 `source`가 `user_verified`가 아니다.
- 이번 요청의 미싱·재조회 목록에 없다(뜻이 바뀌는 중이므로).
- 토큰에 AD-R3 `boundary` 표식이 없다(사용자가 묶은 꼴은 사용자가 뜻을 정한다. 뜻 조회 결과만 쓴다).

후보는 행의 `meanings` 순서대로 최대 3개다. 번호는 1부터이고, 서버는 프롬프트에 실은 그 배열을 응답 검증까지 그대로 들고 있는다.

### 4.2 합친 프롬프트(지금 `buildZhPosPrompt`, `disambiguateZhPos.js:67-102`에 더하는 부분만 굵게)

```
다음은 중국어 문장 목록과, 각 문장에서 품사를 판정할 단어 목록입니다.

## 문장
1. 我给妈妈打了一个电话。
2. 他一个人去旅行。

## 단어
1. "打" (문장 1) 뜻 후보: ①때리다, 치다(동사) ②(전화를) 걸다(동사) ③(운동을) 하다(동사)
2. "电话" (문장 1)
3. "个" (문장 2) [묶음 판정: 个+人]
4. "旅行" (문장 2) 뜻 후보: ①여행하다(동사) ②여행(명사)

각 단어에 대해 JSON 배열로 답하세요.

## 출력 형식 (단어 목록과 순서·길이 정확히 일치)
[
  { "all": ["동사"], "pos": "동사", "sense": 2 },
  { "all": ["명사"], "pos": "명사" },
  { "all": ["양사"], "pos": "양사", "join": false },
  { "all": ["동사", "명사"], "pos": "동사", "sense": 1 }
]

## 규칙
- all, pos, split: (지금 규칙 그대로)
- **sense: 「뜻 후보」가 있는 단어만. 이 문장에서 맞는 후보의 번호(1부터). 맞는 후보가 없으면 0**
- **ctx: sense가 0일 때만. 이 문장에서의 한국어 뜻, 10자 이내**
- **후보 문구를 고쳐 쓰지 말고 번호로만 답할 것. 뜻 후보가 없는 단어에는 sense를 넣지 말 것**
- **join: [묶음 판정] 표시 항목만. 표시된 두 토큰이 이 문장에서 한 단어로 쓰였으면 true, 아니면 false**
- 설명/주석 금지, JSON만 출력
```

- `[묶음 판정]`은 쌍의 앞 토큰 마크에 붙인다. 앞 토큰이 마크가 아니면(个는 양사라 마크 밖) 그 쌍만을 위해 마크를 하나 더한다. 이 마크는 품사 판정 결과를 쓰지 않는다(`pos` 무시). 쌍 수는 요청당 20개로 제한한다. 이 추가 마크는 호출 수를 늘리지 않는다. 다만 같은 요청에 다른 마크가 하나도 없으면 호출 자체가 새로 생기므로, **다른 마크가 있을 때만** 쌍을 싣는다.

### 4.3 응답 검증(순수 함수 `validateSensePick`)

| 입력 | 처리 |
|---|---|
| 응답 배열 길이 ≠ 마크 수 | 전부 버림(지금 규칙) → 현행 |
| `pos ∉ all` | 그 단어 전부 버림(지금 규칙) |
| 후보 없는 단어에 `sense` | 무시 |
| `sense`가 정수 1..n | `meaning = candidates[sense-1].meaning`(문자열 그대로). 후보 `pos`가 있고 판정 `pos`와 다르면 `meaningCheck: 'doubt'` |
| `sense` 범위 밖·비정수·문자열 | **버림** → 그 단어는 `pickZhMeaning` |
| `sense: 0` + `ctx` 1~10자 한국어 | 후보와 정규화가 같으면 그 후보. 아니면 `meaning = ctx`, `meaningCheck: 'ctx'` |
| `sense: 0` + `ctx` 없음·초과·비한글 | 버림 → `pickZhMeaning` + `meaningCheck: 'doubt'` |
| `join: true` | §5.2 규칙 |
| `join` 이 아닌 값 | 무시 |

- 뜻 정규화는 AE-R1 `buildSenseList`의 규칙(괄호 보충 제거 → 쉼표 조각 집합 비교)을 그대로 쓴다. 같은 함수를 import한다(중복 신설 금지).
- `ctx`는 그 토큰에만 남는다. **사전 행에 쓰지 않는다.** 문맥 뜻이 공유 사전에 쌓이면 다른 문장의 「사전 뜻」이 오염된다.

### 4.4 토큰에 남는 것

```jsonc
{ "text": "打", "pos": "동사", "meaning": "(전화를) 걸다", "base_form": "打", "furigana": "dǎ",

```

## 6. 결과 표시

### 6.1 「뜻 확인 필요 N개 [보기]」

- **N** = 이 자료에서 `meaningCheck`가 있는 토큰 수 + `boundarySuggestions` 수. 사용자 교정 토큰은 빠진다(§7).
- **언제**: 분석·재분석이 끝난 직후 한 번. 자리는 본문 위 통계 줄 아래 한 줄이다(AD-R2가 정리한 크롬 안).
- **누구에게**: 자료 소유자만(고칠 수 있는 사람). 열람자에게는 줄을 보이지 않고 카드 ⓘ만 보인다.
- **닫기**: ✕를 누르면 그 자료의 그 `viewerRevision` 동안 다시 띄우지 않는다(localStorage, 개인 편의 — 실패해도 동작에 지장 없음).
- N = 0이면 줄이 없다.

### 6.2 목록 — 그 자리에서 고치기

- [보기]를 누르면 시트의 [문장] 탭 자리에 목록이 열린다(새 화면 아님).
- 줄마다: 문장(그 단어 칠) · 지금 뜻 · 사전 뜻 후보(라디오) · [이대로 둘게요].
- 후보를 누르면 AE-R1 PR③의 사전 뜻 교정 경로(`correctTokenMutation`, `meaning`·`pos`)로 저장하고, 그 토큰의 `meaningCheck`를 지운다. [이대로 둘게요]도 지금 뜻을 확정 교정으로 저장한다.
- 경계 후보 줄: 「身体 素质 → 한 단어로 묶을까요? [묶기] [아니요]」. [묶기]는 AD-R3 확인 줄로 간다. [아니요]는 그 후보를 `boundarySuggestions`에서 지운다(원자 RPC로 저장).

### 6.3 카드

- `meaningCheck`가 있으면 뜻 줄 아래 「ⓘ 문맥과 다를 수 있어요」(정본 §2.1 자리). 사전 뜻 목록에서 다른 뜻을 고르면 사라진다.
- 「AI」 표는 없다(오너 결정).

## 8. 전송 범위

- 중국어는 지금도 문장을 품사 판별에 보낸다(`buildZhPosPrompt`의 문장 목록). 후보 뜻은 우리 사전 데이터라 새로 밖으로 나가는 사용자 데이터가 없다. 범위가 늘지 않는다.
- 일본어는 문장을 LLM에 보내는 분석 단계가 없다. 영어는 품사 판별(`disambiguateEnPos`)이 문장을 보낸다. 두 언어로 넓히는 것은 **오너 결정 대기**다. 서버 분기는 `language === 'Chinese'`일 때만 탄다(계약).
